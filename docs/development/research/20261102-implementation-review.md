## 结论

## 具体问题

1. **单个不可解析 CR 阻塞整个列表。** `pkg/web/server.go` 的 list 对所有 CR 逐一 Refresh，任一错误立即返回。`pkg/gitrepo/repository.go` 的 ResolveBranch 要求本地分支存在。创建 CR 后删除它的源分支，再打开列表，即会走到这个失败路径，其他健康 CR 也不可见。建议列表保留最后发布摘要，为单项附加刷新错误；详情明确报告分支缺失，不伪造新范围。
2. **读取成本随仓库文件数和历史项数放大。** Tree 每次 ls-tree 后，对每个普通文件执行一次 cat-file 并计算内容身份，没有按 tree/OID 缓存。稀疏快照读写经 baseState 再调用 Tree。Review 读取/发布又逐项处理两端快照；列表逐 CR 完整刷新，前端选择项并行请求 diff/threads，两者各自完整 Refresh。源码可确定存在重复工作；本次未做延迟基准，不能给出耗时数字。建议按不可变 OID 缓存树及内容身份，用 cat-file 批量读取；输入签名未变直接复用已发布视图；列表只读摘要，刷新后 diff/threads 读取指定版本。

## 从零开发时的取舍

- 保留真实事件、分批、CR 投影三种不同生命周期，以及 Git 基准加内容寻址存储。它们符合问题本身，不需要推倒重写。
- 分离 Snapshot/ContentResolver、领域状态转换、持久化。当前 Store 同时处理采集状态机、批次约束、投影迁移和审阅，并通过回调访问 Git。尤其 baseState 接收事务对象并调用外部 Git 读取：快照恢复和保存发生在事务内时，锁持有时间被外部进程放大。优先在事务外准备不可变数据，事务内校验 revision/cursor 后提交。
- CR 使用显式的输入版本和不可变投影：先解析分支 OID/读取来源版本，在事务外构建，短事务校验来源并发布。现有版本检查可以保留，但避免每个读取端点都负责重建。
- 将投影诊断结构化，分别记录最终状态闭合与历史归属完整性；不要只用拼接 Warning 字符串。内容已补齐不代表历史解释完整。
- 当前仅允许连续 AI patch 组成 batch，服从最新设计且使状态组合自然。但它表达的是连续开发步骤；交错发生的同一意图不能合并为一个批次。这是产品取舍，不能当作实现 bug，也不能宣称已实现最早概念稿中的任意语义分组。
