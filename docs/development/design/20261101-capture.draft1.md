# 原始变更采集与本地存储

## 已确认的方向

- 一期适配 Codex，后续可扩展 Claude Code 等 Agent 工具。
- 采集不需要预先知道 CR 范围；向上提供与 Agent 工具无关的原始修改记录。
- 本地 SQLite 数据库使用 `~/.motif/data.db`，通过统一存储模块访问。
- 使用 `motif hook` 接收采集入口，使用 `motif install` / `motif uninstall` 安装和卸载项目级集成。
- 每个原始变更记录采集时的 `base_commit`；通过 Git `post-commit` hook 补充最终提交关联。两者都保留，补充提交关联不覆盖原始基准。部分提交通过成对虚拟事件保持事件整体归组，详见整理文档。
- 希望记录实际文件变化、Agent 工具、模型、时间、Git 配置中的人类作者，以及来源确实提供的简要原因。字段是否可取得需要核实。

## 已确认：Git 基准与共享内容库

Motif 在 Git 仓库内运行。快照记录 base commit，以及相对该提交的工作区变更文件路径、当前内容的 SHA-256；内容存入跨仓库、跨快照共享的 SHA-256 blob 库；清理暂留 TODO。未变化文件可由 base commit 读取，无需重复存储。

为保证状态可还原，清单还需表达删除（无内容 hash）、文件类型及 Git mode（如可执行位、符号链接）；这些是恢复状态所需的信息补充。子模块只记录 gitlink，不采集内部变化；采集遵循 Git 忽略规则。Git clean/smudge、换行转换下的原始字节与提交内容关系仍需明确。“全部文件状态”限定为采集范围；一期假定 base commit 对象仍可读取，不处理 Git GC。

一期不支持并发采集，作为已知局限保留；以下状态链按串行操作设计。中断后的缺失事件仍需处理。

## 已确认：快照采集范围与一期保留边界

### 采集范围

采集 base commit 中的路径、当前 index 中的路径，以及未被 Git 忽略的未跟踪文件；读取的是工作区实际内容，不用 index 内容代替工作区。base 中的路径即使已从 index 删除，仍需检查其工作区状态，才能正确表示 staged delete 后文件仍留在磁盘的情况。

- `.git` 及 Git 管理目录不属于代码快照；Motif 数据存放在仓库外。
- 已跟踪文件不因匹配忽略规则而排除。基准或 index 中不存在且被忽略的文件，默认不保存其内容。
- 新增、删除、普通文件、二进制文件、可执行位和符号链接纳入；重命名按删除/新增记录。
- 子模块先记录父仓库中的 gitlink 变化，不递归记录子模块内部未提交内容。需要采集内部内容时，在子模块仓库单独初始化 Motif。
- 不静默跳过大文件。读取或落盘失败时报告本次快照失败，不用缺失内容推进状态链。容量限制和可配置排除机制后续单独定义。

“可还原”限定为上述采集范围，不包括被忽略的缓存、依赖目录等全部磁盘内容。忽略规则导致路径进出采集范围时必须保留范围变动信息，不能将范围外解释成文件已删除；具体清单表达待定。

若用户强制提交之前被忽略的文件，提交 tree 可以补足最终提交内容，但无法追溯采集范围外的中间编辑过程，应显示为缺少过程记录。

### Git GC 与内容清理：TODO

一期不添加额外 Git 引用，不处理 Git GC 对历史基准的影响。读取历史仍依赖原仓库中相应 Git 对象存在；缺失时报告无法读取基准，不伪造内容。

一期不实现快照或 blob 的定期清理、自动过期或通用垃圾回收。Git 基准保留及常规 blob 回收留作 TODO；用户主动执行项目全量卸载时的数据删除属于明确支持的操作，见卸载规则。

## 已确认：在快照边界补记未知来源事件

每次 AI 编辑前，比较本次前置快照与上一次已记录的后置快照。如果存在差异，立即补记一个未知来源修改事件，再记录本次 AI 编辑。未知表示这些变化发生在 Motif 管理的工具调用之外，不推断它们来自人类，也不继承相邻 AI 调用的模型、工具或原因。

```text
上次 AI 后置快照 S1
  --未知事件 Diff(S1, S2)--> 本次 AI 前置快照 S2
  --本次工具期间变化 Diff(S2, S3)--> 本次 AI 后置快照 S3
```

“立即”指在本次前置 hook 发现差异时记录，不表示两次 hook 之间存在实时监控。未知事件的实际发生时间只能限定在两个快照的观测区间内，不能把发现时间当作精确修改时间。该方式记录区间净变化，无法恢复区间内修改后又撤销的过程。

比较需要处于同一工作区及一致的采集范围。一期按串行调用处理，不支持并发归属。

首次采集时，比较 base commit 与首次前置快照，已有差异记为未知来源事件。提交边界根据实际新提交和提交后工作区确定剩余修改及互逆虚拟事件，再计算未知补齐。计算顺序与最终事件重放顺序须区分，详见整理文档。

## 本轮建议，待确认

1. 前后快照的差异首先表示“调用时间窗口内观察到的变化”。遇到并发写入，不能直接声称所有变化均由该调用造成。
2. 原始记录与后续生成的意图分开保存；无法取得的元数据保留未知及来源信息。

## 快照与事件的数据模型提案

本节为下一轮讨论提案，尚未确认为实现契约。

### 身份与工作区游标

数据库为本机全局数据库，不能仅用 commit SHA 区分仓库：不同仓库可以包含同一提交。

- `repository_id`：本机注册的仓库身份。同一 Git common directory 的 linked worktree 共享仓库身份；独立 clone 暂按不同身份注册。远程 URL 是可变元数据，不用作主键。
- `worktree_id`：本机工作区身份，记录工作区路径及 Git directory。一个仓库可有多个工作区，每个工作区有独立采集游标；一期不保证并发写入同一工作区的归属。
- `cursor`：当前 base commit、上一个观测快照、调用上下文及递增版本号。它是可变处理状态；历史快照、事件不可变。不额外引入 capture segment 实体。

### 快照

```text
Snapshot
  id, repository_id, worktree_id?
  base_commit_oid
  observed_at, scope_version
  trigger, tool_call_id?, tool_context
  session_id?, turn_id?
  entries[]

SnapshotEntry
  path
  operation: upsert | delete
  git_mode                 # upsert 时必需
  blob_sha256              # 普通文件/符号链接 upsert 时必需
```

每份 entries 是相对 base commit 的完整覆盖清单，不是相对上一快照的增量。删除条目表示移除基准中的路径；未出现的路径继承基准。文件恢复至基准状态后不再出现。重命名可用删除与新增精确表示，是否展示为 rename 是后续 diff 逻辑。

空文件有正常的 SHA-256；delete 不使用空文件 hash。符号链接内容是链接目标的字节，不跟随链接读取外部文件。只改变可执行位也需要 upsert 条目。若支持子模块，应另存 gitlink OID，不能将目录当普通 blob；是否进入一期待定。

路径相对工作区根，保留大小写和原始字节；SQLite 可用 BLOB 保存，协议/UI 层另定义非 UTF-8 路径的编码，避免路径归一化导致两个文件合并。

提交 tree 也可表示为一份 entries 为空、base_commit 为该提交的快照。相同文件状态可以有不同基准表示；比较快照时解析实际状态，不能只比较 snapshot ID 或覆盖清单。

### 已确认：连续快照产生修改事件

主流程只维护按观测顺序排列的快照。PreToolUse、PostToolUse、Git post-commit 等都是写入新快照的触发入口；写入后一个快照时，计算它与上一个快照的差异并记录修改事件。有快照而无内容变化时可不生成修改事件。

快照同时保存 `trigger` 及触发时的工具上下文。事件归属取决于两个快照之间的调用上下文，不单凭后一个快照的名称：PreToolUse 写下前的区间通常为未知；PreToolUse 写下后到对应 PostToolUse 之间为 AI。post-commit 若发生在调用期间，前后区间继续属于同一调用；若发生在调用之外，则前面的未采集变化为未知。

```text
Pre(S1) → Post(S2) → Commit(S3)
    AI          未知

Pre(S1) → Commit(S2) → Post(S3)
    AI            AI（同一调用、同一原因）
```

提交只是普通观测触发入口加上提交关联逻辑。无需先定义“工具片段”才能生成事件，也不需要单独维护工具片段起点；上一个观测快照就是下一个事件的起点。部分提交另加虚拟事件，不改变真实观测快照的顺序。

### 修改事件与工具调用

```text
ChangeEvent
  id, worktree_id, sequence
  kind: tool_edit | unknown | virtual_close | virtual_carry
  base_commit_oid
  before_snapshot_id, after_snapshot_id
  detected_at, observed_from, observed_until
  tool_call_id?             # 仅有可靠来源时设置
  virtual_pair_id?          # 成对虚拟事件
  reason_code?              # 如 external_gap / initial_dirty / commit_gap

ToolCall
  id, adapter, session_id, external_call_id
  turn_id
  agent_id?, model?, tool_name, tool_input?
  explanation?, explanation_source?
  git_user_name?, git_user_email?
  started_at, finished_at?, status
  pre_snapshot_id?, post_snapshot_id?
```

- 事件的真实变化由前后快照定义；文本 patch 按需生成或缓存，不作为唯一事实来源。这样二进制、无上下文 patch 和逆变换均可由状态表示。
- 工具调用与事件分开：无变化调用仍可有调用记录，不生成空修改事件。一次调用也可能因为中途提交被边界切分为多段事件。
- `sequence` 表示工作区内记录顺序；时间字段用于解释观测区间，不替代排序。未知事件不自动关联相邻工具调用。
- 原因、模型缺失时存 NULL。Git user 是采集时读取的配置值，不声称是操作人的身份认证。虚拟事件不继承虚构的 Agent 元数据。
- base commit 是原始观测上下文。未来 rebase 通过独立的提交投影复用事件，不能修改原始 before/after 或 base commit 来伪造历史。

### SQLite 表职责

| 表 | 主要内容与约束 |
|---|---|
| repositories / worktrees | 本机身份、定位信息，worktree 属于 repository |
| worktree_cursors | 上一个观测快照、当前 base、调用上下文和版本，每个工作区一条 |
| snapshots / snapshot_entries | 基准及覆盖清单；条目主键为 snapshot + path |
| blobs | SHA-256、长度及完整落盘状态；全局去重 |
| tool_calls | adapter + session + external call ID 的幂等身份，归入本机工作区上下文 |
| edit_events | 前后快照、来源类型、工作区内唯一 sequence；此前模型中的 ChangeEvent 对应此表 |
| turns / patch_batches / patch_batch_members | 轮次、AI/未知批次、有序成员及整理说明，详见整理文档 |
| virtual_pairs | close/carry 事件对应关系 |
| commit_projections / commit_projection_events | 仓库、提交、比较父节点、投影版本；有序事件引用及验证状态 |
| hook_receipts | hook 幂等键、输入摘要、已完成操作结果 |
| schema_migrations | 数据库迁移版本 |

提交投影单独保存事件引用：正常提交绑定待关联事件集合，历史改写可建立新投影，复用原始事件及补充事件；保留旧投影。具体 rebase 规则仍在整理文档中细化。常用索引包括仓库+提交、工作区+sequence、工具调用外部身份及快照 blob 引用。不建通用无约束 JSON 表替代核心关系；adapter 特有扩展可存 JSON。

### Blob 库与持久化顺序

建议目录：`~/.motif/blobs/sha256/<前两位>/<剩余62位>`，存原始字节，hash 对原始字节计算；数据库保存引用和大小。临时内容位于同一文件系统的临时目录。

写入顺序：读取并计算 hash → 写临时文件并同步 → 原子发布 blob → SQLite 事务保存快照、事件及游标。进程中断最多留下无引用 blob，不能提交指向尚未落盘内容的快照。读取错误或不完整快照不能当作空 diff 推进游标。

一期不实现常规 GC，不添加 Motif 私有 Git 引用；基准保留和定期 blob 清理均留作 TODO。全量卸载删除当前项目数据时需单独处理相关 blob，不能影响其他项目的引用。

Git clean/smudge、LFS、换行转换可能导致提交字节与工作区字节不同。上述 blob 保存观测原始字节；正式确定“继承 base”的解析与提交对比规则前，不能声明这些仓库已支持精确还原。不得在 hash 前静默转换内容。

## 统一存储模块接口提案

建议由 `pkg/store` 封装 SQLite 与 blob 访问，调用方不持有 SQL 连接。Git 读取、快照计算和 Codex 协议解析分别放在独立模块；store 不调用 Agent，也不执行 Git 工作区修改。

```go
type Store interface {
    PutBlob(ctx context.Context, content io.Reader) (BlobRef, error)
    OpenBlob(ctx context.Context, hash SHA256) (io.ReadCloser, error)
    View(ctx context.Context, fn func(Reader) error) error
    Update(ctx context.Context, fn func(Tx) error) error
    Close() error
}
```

接口仅表达边界，具体 Go 类型待表结构敲定。Reader 提供游标、快照、调用、事件及提交投影查询；Tx 提供以下原子操作，内部封装多表更新：

- `RecordSnapshot`：统一保存观测快照、生成与上一快照之间的事件、记录来源及更新调用上下文和游标；前后置 hook 复用该操作。
- `FinalizeCommit`：复用相同的快照记录规则，再补充 Q/P、绑定提交事件集合、更新 base；所有状态修改在同一事务完成，不维护额外工具片段游标。
- `RecordGitTransition`：记录 HEAD/历史映射并切换采集基准，具体恢复规则待细化。

计算文件差异在事务外完成，事务内验证预期游标版本；不匹配则重新观测，不能强行写入旧结果。hook 幂等凭据与状态修改同事务提交；重复输入返回已完成结果，相同幂等键而内容不同则报冲突。失败不得部分绑定事件，也不回滚 Git 已完成的提交。未实现的迁移版本、blob 缺失、基准对象缺失及游标冲突应有可区分错误。

## 已确认：工具调用内的提交无需独立切段机制

串行模式也存在嵌套边界：AI 的 Bash 调用可能先编辑再执行 git commit，post-commit 早于外层 PostToolUse。

提交 hook 读取当前工作区的调用状态，按两种情况处理：

```text
case 1：调用已结束
PreToolUse(S1) → AI 修改 → PostToolUse(S2) → 外部修改 → commit(R)
  S1→S2：已记录的 AI 事件
  S2→R ：提交边界补记的未知事件

case 2：调用尚在进行
PreToolUse(S1) → AI 修改 → commit(S2) → AI 修改 → PostToolUse(S3)
  S1→S2：提交边界记录的 AI 片段，归入本次提交
  S2→S3：调用结束记录的 AI 片段，留在新提交为 base 的后续段
```

两个相邻快照事件关联同一 ToolCall，沿用相同原因及来源元数据（原始原因缺失时仍为空）。提交时调用仍然进行，最新观测快照自然变成 S2；PostToolUse 只比较上一快照 S2 与新快照 S3。原始 pre_snapshot S1 不覆盖，也不另设 fragment_start_snapshot。一次调用多次提交时仍使用同一规则。

S2 指 post-commit 时实际工作区快照，不必等于新提交 tree。部分提交时，旧段仍在 AI 片段后追加 virtual_close，新段先记录 virtual_carry，再衔接 S2→S3。两个虚拟事件单独标记，不继承 AI 原因。若需要以新 base 表示 S2，可保存内容等价的新基准快照，而不修改旧快照。

一期串行假设下，工具期间的变化统一按工具事件归属，不额外推断其中由命令启动的格式化等子步骤。独立于工具调用发生的变化才补为未知来源。

缺少 PostToolUse 的失败/中断调用按下一节降级处理，不将永久遗留的 open 记录当作正在执行的证据。

### 已确认：缺失后置事件的降级

失败或中断后无法可靠归属的变化记为未知，不沿用遗留调用的 AI 原因。新的 PreToolUse 到达而上一个调用仍缺少结束记录时，先将旧调用标为 incomplete；上次已确认快照到当前前置快照的变化记为未知，再开启新调用。Interrupt/SessionEnd 可以辅助清除失效上下文，但不能假定每次退出都收到通知。

单凭数据库中存在 open 行不能证明调用仍在执行。post-commit 内的 AI 归属还需有当前执行上下文的调用身份匹配；无法确认时降级 unknown。正常串行工具内提交仍按之前已确认规则处理。迟到 PostToolUse 不得覆盖已补齐历史或再次计算同一变化。

## 存储设计 v1：字段、约束与接口提案

以下为第 7 项的首版具体设计，待讨论，不表示已经实现或最终采用。仅保存仓库外 SQLite 与内容库，不为每种来源另建一套编辑数据。

### 公共约定

- UID 使用随机 UUID 字符串，列表同时显示完整 UID；Git OID 用 TEXT，不写死 40 位。SHA-256 用 64 位小写十六进制 TEXT。
- 时间为 UTC 微秒 INTEGER。所有归属排序以显式 sequence/position 为准，不能用时间戳唯一排序。
- 路径存 BLOB，CLI JSON 另提供可逆编码；文件状态含 operation、git_mode、blob hash 或 gitlink OID。
- 外键与唯一约束在事务内执行；JSON 只存原始 adapter 扩展，核心关系单独列。批次成员不能只存一串逗号分隔 UID。

### 表结构

| 表 | 主要字段（PK 为主键，FK 为引用） |
|---|---|
| repositories | id PK, git_common_dir UNIQUE, object_format, created_at；origin URL 只是可变元信息 |
| worktrees | id PK, repository_id FK, root_path, git_dir UNIQUE, created_at |

### 约束与写事务

- delete entry 的 mode/hash/gitlink 都为空；普通文件/符号链接 upsert 需要 mode 与 blob；gitlink 需要对应 OID。base 中删除与空文件不能混淆。
- tool_edit 必须有可信调用及轮次引用；unknown 不借用相邻调用身份；virtual 必须有配对与系统来源标记。
- edit_events.turn_id 对 AI 表示来源轮次；对 unknown 仅表示在哪一轮的边界被发现，用于本轮列表展示，不代表该轮 Agent 编写。没有观测轮次则为空；未知 batch 自身允许成员来自多个观测轮次。
- AI batch 的所有成员必须同轮、同工作区、同一提交边界且连续；unknown batch 允许跨轮，不跨 commit。此类跨行规则由事务内查询校验，不能仅靠表字段声称已满足。
- final_commit 仅由提交关联操作补充，原始 base 不覆盖；commit/projection 的仓库身份必需一致。历史改写新增来源记录/投影，而非覆盖旧行。
- RecordSnapshot 同事务写入快照、条目、实际差异事件、未知自动归组、调用上下文、receipt 和游标；内容 hash 对象须先完整落盘。无变化仍保存触发快照，不新增空 patch。
- FinalizeCommit 同事务补充提交快照事件、Q/P、关联待提交事件及 batch、写投影、更新 base。不能先标“已关联”再补虚拟事件。事件集合以当前工作区游标和未关联集合锁定，不扫描所有同 base 的历史事件。
- CreateBatch/DeleteBatch 分别原子更新 batch 与成员，不修改文件；同一校验过程对所有成员成功后才写入。

### 模块与接口

建议模块职责：`pkg/agent` 解析事件和输出 hook 协议；`pkg/git` 读取树、工作区及 hook 通知；`pkg/capture` 串联连续快照；`pkg/patch` 处理查询、批次约束；`pkg/review` 构建 CR 及审阅状态；`pkg/store` 统一持久化。调用方不直接操作 SQL，Git/Agent 调用不放进数据库事务。

```text
Store.Open(data_dir) / Close()
Store.PutBlob(reader) / OpenBlob(hash)
Store.View(reader => result)
Store.Update(tx => result)

Reader.GetCursor(worktree)
Reader.GetSnapshot(uid) / ListSnapshotEntries(uid)
Reader.ResolveTurn(caller_identity)
Reader.ListPatches(filter) / GetPatch(uid)
Reader.GetBatch(uid) / ListBatches(filter)
Reader.GetCommitProjection(repository, oid, parent)

Tx.RecordSnapshot(prepared_snapshot, expected_cursor_version, hook_receipt)
Tx.FinalizeCommit(prepared_commit, expected_cursor_version, hook_receipt)
Tx.CreateBatch(validated_request)
Tx.DeleteBatch(uid)
Tx.RecordRewrite(mapping, prepared_projections)
```

prepared 数据由服务层在事务外读取 Git、计算 hash/diff 后构建；Tx 重新检查当前游标和成员归属，冲突时不写入过时结果。Tx.RecordSnapshot/FinalizeCommit 内复用快照持久化逻辑，避免开启嵌套事务。CR 的 store 方法与服务接口见 Web 文档。

错误至少区分 NotFound、InvalidArgument、Conflict、MissingBlob、MissingGitObject、StorageFailure。普通 CLI 输出错误并返回非零；hook 适配器负责故障放行或正常 Stop block，不能把 store 错误直接当作“未完成分批”。

### Hook 与 CLI 返回契约提案

普通 CLI 成功返回 0，参数或规则校验失败返回 2，执行失败返回 1；支持 `--format json` 的查询输出包含稳定字段和完整 UID。默认文本面向 coding Agent 阅读。安装/卸载的交互及确认保持既定规则，非终端需要显式参数。

Codex hook 接收一份 stdin JSON，按事件分派。普通采集成功/故障放行均不输出控制 JSON；正常 Stop 未分批返回退出码 0 + `{decision:block,reason:...}`，全部完成返回空输出或明确放行。stdout 只用于协议，日志写 stderr/本地日志。Git hook 原样接收 argv/stdin，Motif 自身失败不改变已有其他 hook 的行为。

幂等身份建议：工具前后置使用 worktree + session + turn + call + event；Stop 可能在同一轮多次发生，不得仅用 turn ID 去重，应重新读取当前待分批状态；post-rewrite 按一次操作及有序映射去重。具体无法从输入唯一识别的通知需基于已应用状态判断，不把相同 commit OID 当作所有通知的同一个事件。

## Hook 命令与项目级安装、卸载

### Hook 命令

建议按来源区分入口，复用统一快照记录逻辑：

```sh
motif hook codex
motif hook git post-commit
motif hook git post-rewrite <git原始参数...>
motif hook git post-checkout <old-head> <new-head> <flag>
motif hook git reference-transaction <phase>
```

`motif hook codex` 从 stdin 读取 Codex 原始 JSON，根据 `hook_event_name` 分派，不要求配置中重复声明事件；匹配调用使用 session_id + tool_use_id。适配层解析为统一触发上下文，快照和存储模块不依赖 Codex 字段名称。工作区优先依据 payload 的 cwd 定位，不假定 hook 进程 cwd 等于工具执行目录。

Git 入口按 Git 实际 hook 点设置，不按操作类型拆入口。amend/rebase 共用一个 post-rewrite hook，Git 将操作类型作为第一个参数传入；Motif 在内部解析类型及 stdin 中的提交映射。post-commit 无参数。只有需要观测工作区的入口写快照，引用事务等通知不能无条件当作完整操作结束。具体 Git 操作处理规则仍在提交关联文档细化。

已确认：生成的 hook 脚本只调用一次对应 Motif 入口，原样转发参数与 stdin，不承担事件分类、映射解析、快照或数据库处理。例如 post-rewrite 的 Motif 调用为：

```sh
motif hook git post-rewrite "$@"
```

无需在脚本中对 amend/rebase 分支。已有其他 hook 的串接是安装器的兼容职责，不要求用户编写上述业务逻辑。

### 已确认：采集失败放行，Stop 正常检查可要求分批

自动安装的 Motif hook，采集、数据库或命令执行失败时不阻断 Agent 工作及 Git 操作。缺少记录可以接受；不能为了保证采集完整而阻断编辑或提交。失败快照不推进游标；后续若能补齐净变化则补齐，不能声称恢复了全部中间过程。

普通采集 hook 的 stdout 不注入上下文、不修改工具参数或阻断；错误诊断使用 stderr 或本地日志。不阻断约定需要覆盖 Motif 命令不存在、启动失败和超时等情况，而不只覆盖程序内部已捕获的异常；各 Agent 的返回协议和超时配置仍需集成验证。已有其他 hook 的语义保持不变。

Stop hook 是明确的业务例外：成功查询到本轮仍有未分批 AI patch 时，输出包含列表及命令指引的结构化 block，让 coding Agent 在同一轮继续完成分批。全部完成后放行；查询/存储异常仍放行。详见整理文档。install 应同时配置此同步 Stop hook。

用户查看时，无采集记录应提示“未采集到数据，可能未安装 hook 或 hook 运行失败”。若没有明确诊断，不断言是哪一种原因；存在部分记录也不能据此保证全过程已采集。具体状态展示见 Web 文档。

### 已确认：motif install

仅配置当前项目，暂不支持全局作用域。命令统一命名为 install；讨论中沿用旧名的 `motif init --agent ...` 示例按新命名记录，不据此引入 init 别名。

```sh
motif install
motif install --agent codex
motif install --agent codex --agent claude-code
```

- 无 `--agent`：检测环境中可发现的受支持 Agent 工具，列出多选菜单；默认勾选已安装的工具。未安装不妨碍为其生成配置，菜单仍可手动选择。
- 重复 `--agent`：直接配置指定集合，跳过交互选择；不要求对应 Agent 已安装。去重参数，不因未选择而移除其他已有配置。
- 安装只增不删，幂等执行。对已经配置的 Agent 跳过，不重复追加 hook，不重写用户其他配置。
- 默认同时确保本项目所需的共享 Git hook 已安装；共享 hook 不随 Agent 数量重复安装。保留已有 hook 与 core.hooksPath；串接逻辑由安装器处理，脚本不承担采集业务。
- 输出每个 Agent 的新增、已配置跳过或失败结果。配置缺失、冲突或损坏不应仅凭数据库安装标记当作成功；具体检测及修复规则待定。

本期实际适配范围仍为 Codex。Claude Code 示例表达可扩展的参数形式，只有适配器实现后才进入可配置列表；不把“未安装但支持配置”混同于“尚未实现支持”。未知或未实现 Agent 必须明确报错，不能假装配置成功。

### 已确认：motif uninstall

```sh
motif uninstall
motif uninstall --agent codex
motif uninstall -y
motif uninstall --agent codex -y
```

- 不带 `--agent` 为全量卸载：移除当前项目的全部 Motif 集成，并删除当前项目的数据，尽量恢复安装前状态。全量卸载即使已无 Agent 配置，也应检查并计划删除残留项目数据。
- 指定 `--agent` 时只移除对应集合，参数可重复，不删除项目历史数据；即使显式参数恰好选中了所有 Agent，也不等同于不带参数的全量卸载。
- 执行前列出受影响 Agent、实际配置文件路径及具体 Motif 配置（包含 hook）；共享 Git hook 若会移除也列出。全量卸载的清单还必须列出将删除的数据范围，明确此操作删除历史数据，而不只是解除配置。
- 默认按 Y 确认后才修改；拒绝或取消时不做删除。`-y` 跳过确认，仍输出移除清单。
- 只删除 Motif 管理的配置，保留用户其他配置和 hook；没有配置或数据时报告无对应移除项。

全量卸载的数据范围为当前本机注册仓库（repository_id）的记录，包括其工作区记录、快照、事件、工具调用及已生成的整理/审阅结果等关联数据。`~/.motif/data.db` 和 blob 库由所有项目共享，不直接删除整个数据库文件或 blob 目录；其他仓库的数据不受影响。删除当前项目引用后，仅删除没有任何保留引用的相关 blob，共享 blob 继续保留。该引用检查用于本次显式删除，不扩展为定期 GC。

确认清单应显示项目范围、涉及的本地工作区、数据库位置、待删记录类别/数量，以及将删除的独占 blob 和保留的共享内容；准确数量可在执行前计算。用户应在确认前看见数据删除后果。`-y` 仍输出同样清单，但不等待再次确认。

### 安装卸载的实现建议，待确认

1. install 没有终端且未提供 `--agent` 时，返回提示使用显式参数，不等待交互；uninstall 无终端且未提供 `-y` 时不执行删除。
2. 全部 Agent 卸载后移除本项目共享的 Motif Git hook；仍有 Agent 集成时保留。全量卸载按上述规则删除项目数据，指定 Agent 卸载保留数据。恢复安装器创建的文件或配置项时不覆盖用户后续修改，不能安全恢复则明确报告残留。
3. install 只负责安装配置，是否额外建立首次快照尚待确认；不能将此前的首次快照建议当作用户已确认。首次真正采集仍须从 base commit 补齐已有修改。
4. 原有安装配置由用户改动时，列出差异或冲突，不盲目覆盖；具体管理标记和配置文件写入方式需结合 Agent 协议确定。

## 下一步逐项细化
