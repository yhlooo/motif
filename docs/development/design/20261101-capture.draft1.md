# 原始变更采集与本地存储

状态：讨论草案，不作为实现依据。配套文档：[整理](20261101-organization.draft1.md)、[本地 Web](20261101-web.draft1.md)。

## 已确认的方向

- 一期适配 Codex，后续可扩展 Claude Code 等 Agent 工具。
- 采集不需要预先知道 CR 范围；向上提供与 Agent 工具无关的原始修改记录。
- 本地 SQLite 数据库使用 `~/.motif/data.db`，通过统一存储模块访问。
- 使用 `motif hook` 接收采集入口，使用 `motif init` 帮助配置集成。
- 每个原始变更记录采集时的 `base_commit`；通过 Git `post-commit` hook 补充最终提交关联。两者都保留，补充提交关联不覆盖原始基准。部分提交通过成对虚拟事件保持事件整体归组，详见整理文档。
- 希望记录实际文件变化、Agent 工具、模型、时间、Git 配置中的人类作者，以及来源确实提供的简要原因。字段是否可取得需要核实。

## 外部能力核实

见 [Codex 与 Git Hook 研究](../research/20261101-codex-git-hooks.md)。官方 main 源码确认存在 PreToolUse/PostToolUse 和模型、调用 ID 等输入字段；没有通用实际 diff，失败可能缺少后置事件。当前结论尚非已发布 CLI 的集成验证。

## 已确认：Git 基准与共享内容库

Motif 在 Git 仓库内运行。快照记录 base commit，以及相对该提交的工作区变更文件路径、当前内容的 SHA-256；内容存入跨仓库、跨快照共享的 SHA-256 blob 库，按引用定期清理。未变化文件可由 base commit 读取，无需重复存储。

为保证状态可还原，清单还需表达删除（无内容 hash）、文件类型及 Git mode（如可执行位、符号链接）；这些是恢复状态所需的信息补充。子模块 gitlink、忽略文件是否属于采集范围，以及 Git clean/smudge、换行转换下的原始字节与提交内容关系，仍需明确；“全部文件状态”仅能在明确采集范围后成立。base commit 对象必须保持可读，GC 方案还需保证这一点。

一期不支持并发采集，作为已知局限保留；以下状态链按串行操作设计。中断后的缺失事件仍需处理。

## 待确认：快照采集范围与保留规则

本节为讨论建议，不改变已确认的连续快照模型。

### 采集范围

建议采集 base commit 中的路径、当前 index 中的路径，以及未被 Git 忽略的未跟踪文件；读取的是工作区实际内容，不用 index 内容代替工作区。base 中的路径即使已从 index 删除，仍需检查其工作区状态，才能正确表示 staged delete 后文件仍留在磁盘的情况。

- `.git` 及 Git 管理目录不属于代码快照；Motif 数据存放在仓库外。
- 已跟踪文件不因匹配忽略规则而排除。基准或 index 中不存在且被忽略的文件，默认不保存其内容。
- 新增、删除、普通文件、二进制文件、可执行位和符号链接纳入；重命名按删除/新增记录。
- 子模块先记录父仓库中的 gitlink 变化，不递归记录子模块内部未提交内容。需要采集内部内容时，在子模块仓库单独初始化 Motif。
- 不静默跳过大文件。读取或落盘失败时报告本次快照失败，不用缺失内容推进状态链。容量限制和可配置排除机制后续单独定义。

“可还原”限定为上述采集范围，不包括被忽略的缓存、依赖目录等全部磁盘内容。忽略规则导致路径进出采集范围时必须保留范围变动信息，不能将范围外解释成文件已删除；具体清单表达待定。

若用户强制提交之前被忽略的文件，提交 tree 可以补足最终提交内容，但无法追溯采集范围外的中间编辑过程，应显示为缺少过程记录。

### 基准对象保留

建议对仍被快照引用的 base commit 在其仓库中创建 `refs/motif/bases/<oid>` 私有引用。引用用于防止对象被 GC，不修改 HEAD、分支、index 或工作区；默认不推送。清理时仅在没有任何保留记录引用该基准后删除对应 Motif 引用，不自动执行 Git GC。

这使快照依赖本地 Git 对象库；删除仓库后不能仅靠 data.db 和增量 blob 还原全部历史。跨机器搬迁或仓库删除后仍可阅读的归档能力后续另定。

### 清理

默认不自动删除历史事件和仍被引用的内容。定期清理仅回收无引用 blob、临时文件和不再需要的 Motif 基准引用；自动回收的调度入口、显式删除历史命令及保留期限另行设计。不能按 blob 的创建时间直接删除，也不能在回收期间删除尚未完成快照发布的内容。

## 已确认：在快照边界补记未知来源事件

每次 AI 编辑前，比较本次前置快照与上一次已记录的后置快照。如果存在差异，立即补记一个未知来源修改事件，再记录本次 AI 编辑。未知表示这些变化发生在 Motif 管理的工具调用之外，不推断它们来自人类，也不继承相邻 AI 调用的模型、工具或原因。

```text
上次 AI 后置快照 S1
  --未知事件 Diff(S1, S2)--> 本次 AI 前置快照 S2
  --本次工具期间变化 Diff(S2, S3)--> 本次 AI 后置快照 S3
```

“立即”指在本次前置 hook 发现差异时记录，不表示两次 hook 之间存在实时监控。未知事件的实际发生时间只能限定在两个快照的观测区间内，不能把发现时间当作精确修改时间。该方式记录区间净变化，无法恢复区间内修改后又撤销的过程。

比较需要处于同一工作区及一致的采集范围。一期按串行调用处理，不支持并发归属。

首次采集时，比较 base commit 与首次前置快照，已有差异记为未知来源事件。提交边界根据实际新提交和提交后工作区确定剩余修改及互逆虚拟事件，再计算未知补齐。计算顺序与最终事件重放顺序须区分，详见整理文档。

## 本轮建议，待确认

1. 前后快照的差异首先表示“调用时间窗口内观察到的变化”。遇到并发写入，不能直接声称所有变化均由该调用造成。
2. 原始记录与后续生成的意图分开保存；无法取得的元数据保留未知及来源信息。

## 快照与事件的数据模型提案

本节为下一轮讨论提案，尚未确认为实现契约。

### 身份与工作区游标

数据库为本机全局数据库，不能仅用 commit SHA 区分仓库：不同仓库可以包含同一提交。

- `repository_id`：本机注册的仓库身份。同一 Git common directory 的 linked worktree 共享仓库身份；独立 clone 暂按不同身份注册。远程 URL 是可变元数据，不用作主键。
- `worktree_id`：本机工作区身份，记录工作区路径及 Git directory。一个仓库可有多个工作区，每个工作区有独立采集游标；一期不保证并发写入同一工作区的归属。
- `cursor`：当前 base commit、上一个观测快照、调用上下文及递增版本号。它是可变处理状态；历史快照、事件不可变。不额外引入 capture segment 实体。

### 快照

```text
Snapshot
  id, repository_id, worktree_id?
  base_commit_oid
  observed_at, scope_version
  trigger, tool_call_id?, tool_context
  entries[]

SnapshotEntry
  path
  operation: upsert | delete
  git_mode                 # upsert 时必需
  blob_sha256              # 普通文件/符号链接 upsert 时必需
```

每份 entries 是相对 base commit 的完整覆盖清单，不是相对上一快照的增量。删除条目表示移除基准中的路径；未出现的路径继承基准。文件恢复至基准状态后不再出现。重命名可用删除与新增精确表示，是否展示为 rename 是后续 diff 逻辑。

空文件有正常的 SHA-256；delete 不使用空文件 hash。符号链接内容是链接目标的字节，不跟随链接读取外部文件。只改变可执行位也需要 upsert 条目。若支持子模块，应另存 gitlink OID，不能将目录当普通 blob；是否进入一期待定。

路径相对工作区根，保留大小写和原始字节；SQLite 可用 BLOB 保存，协议/UI 层另定义非 UTF-8 路径的编码，避免路径归一化导致两个文件合并。

提交 tree 也可表示为一份 entries 为空、base_commit 为该提交的快照。相同文件状态可以有不同基准表示；比较快照时解析实际状态，不能只比较 snapshot ID 或覆盖清单。

### 已确认：连续快照产生修改事件

主流程只维护按观测顺序排列的快照。PreToolUse、PostToolUse、Git post-commit 等都是写入新快照的触发入口；写入后一个快照时，计算它与上一个快照的差异并记录修改事件。有快照而无内容变化时可不生成修改事件。

快照同时保存 `trigger` 及触发时的工具上下文。事件归属取决于两个快照之间的调用上下文，不单凭后一个快照的名称：PreToolUse 写下前的区间通常为未知；PreToolUse 写下后到对应 PostToolUse 之间为 AI。post-commit 若发生在调用期间，前后区间继续属于同一调用；若发生在调用之外，则前面的未采集变化为未知。

```text
Pre(S1) → Post(S2) → Commit(S3)
    AI          未知

Pre(S1) → Commit(S2) → Post(S3)
    AI            AI（同一调用、同一原因）
```

提交只是普通观测触发入口加上提交关联逻辑。无需先定义“工具片段”才能生成事件，也不需要单独维护工具片段起点；上一个观测快照就是下一个事件的起点。部分提交另加虚拟事件，不改变真实观测快照的顺序。

### 修改事件与工具调用

```text
ChangeEvent
  id, worktree_id, sequence
  kind: tool_edit | unknown | virtual_close | virtual_carry
  base_commit_oid
  before_snapshot_id, after_snapshot_id
  detected_at, observed_from, observed_until
  tool_call_id?             # 仅有可靠来源时设置
  virtual_pair_id?          # 成对虚拟事件
  reason_code?              # 如 external_gap / initial_dirty / commit_gap

ToolCall
  id, adapter, session_id, external_call_id
  agent_id?, model?, tool_name, tool_input?
  explanation?, explanation_source?
  git_user_name?, git_user_email?
  started_at, finished_at?, status
  pre_snapshot_id?, post_snapshot_id?
```

- 事件的真实变化由前后快照定义；文本 patch 按需生成或缓存，不作为唯一事实来源。这样二进制、无上下文 patch 和逆变换均可由状态表示。
- 工具调用与事件分开：无变化调用仍可有调用记录，不生成空修改事件。一次调用也可能因为中途提交被边界切分为多段事件。
- `sequence` 表示工作区内记录顺序；时间字段用于解释观测区间，不替代排序。未知事件不自动关联相邻工具调用。
- 原因、模型缺失时存 NULL。Git user 是采集时读取的配置值，不声称是操作人的身份认证。虚拟事件不继承虚构的 Agent 元数据。
- base commit 是原始观测上下文。未来 rebase 通过独立的提交投影复用事件，不能修改原始 before/after 或 base commit 来伪造历史。

### SQLite 表职责

| 表 | 主要内容与约束 |
|---|---|
| repositories / worktrees | 本机身份、定位信息，worktree 属于 repository |
| worktree_cursors | 上一个观测快照、当前 base、调用上下文和版本，每个工作区一条 |
| snapshots / snapshot_entries | 基准及覆盖清单；条目主键为 snapshot + path |
| blobs | SHA-256、长度及完整落盘状态；全局去重 |
| tool_calls | adapter + session + external call ID 的幂等身份，归入本机工作区上下文 |
| change_events | 前后快照、来源类型、工作区内唯一 sequence |
| virtual_pairs | close/carry 事件对应关系 |
| commit_projections / commit_projection_events | 仓库、提交、比较父节点、投影版本；有序事件引用及验证状态 |
| hook_receipts | hook 幂等键、输入摘要、已完成操作结果 |
| schema_migrations | 数据库迁移版本 |

提交投影单独保存事件引用：正常提交绑定待关联事件集合，历史改写可建立新投影，复用原始事件及补充事件；保留旧投影。具体 rebase 规则仍在整理文档中细化。常用索引包括仓库+提交、工作区+sequence、工具调用外部身份及快照 blob 引用。不建通用无约束 JSON 表替代核心关系；adapter 特有扩展可存 JSON。

### Blob 库与持久化顺序

建议目录：`~/.motif/blobs/sha256/<前两位>/<剩余62位>`，存原始字节，hash 对原始字节计算；数据库保存引用和大小。临时内容位于同一文件系统的临时目录。

写入顺序：读取并计算 hash → 写临时文件并同步 → 原子发布 blob → SQLite 事务保存快照、事件及游标。进程中断最多留下无引用 blob，不能提交指向尚未落盘内容的快照。读取错误或不完整快照不能当作空 diff 推进游标。

GC 必须与发布快照互斥：先标记保留的快照及其 blob，再删除无引用且经过宽限期的对象。定期清理不是按 blob 年龄直接删除。删除快照/历史的保留策略另定。Git 基准对象也必须保留；可在各仓库维护 Motif 私有 refs 固定基准，但这一仓库元数据写入方案尚待确认。

Git clean/smudge、LFS、换行转换可能导致提交字节与工作区字节不同。上述 blob 保存观测原始字节；正式确定“继承 base”的解析与提交对比规则前，不能声明这些仓库已支持精确还原。不得在 hash 前静默转换内容。

## 统一存储模块接口提案

建议由 `pkg/store` 封装 SQLite 与 blob 访问，调用方不持有 SQL 连接。Git 读取、快照计算和 Codex 协议解析分别放在独立模块；store 不调用 Agent，也不执行 Git 工作区修改。

```go
type Store interface {
    PutBlob(ctx context.Context, content io.Reader) (BlobRef, error)
    OpenBlob(ctx context.Context, hash SHA256) (io.ReadCloser, error)
    View(ctx context.Context, fn func(Reader) error) error
    Update(ctx context.Context, fn func(Tx) error) error
    Close() error
}
```

接口仅表达边界，具体 Go 类型待表结构敲定。Reader 提供游标、快照、调用、事件及提交投影查询；Tx 提供以下原子操作，内部封装多表更新：

- `RecordSnapshot`：统一保存观测快照、生成与上一快照之间的事件、记录来源及更新调用上下文和游标；前后置 hook 复用该操作。
- `FinalizeCommit`：复用相同的快照记录规则，再补充 Q/P、绑定提交事件集合、更新 base；所有状态修改在同一事务完成，不维护额外工具片段游标。
- `RecordGitTransition`：记录 HEAD/历史映射并切换采集基准，具体恢复规则待细化。

计算文件差异在事务外完成，事务内验证预期游标版本；不匹配则重新观测，不能强行写入旧结果。hook 幂等凭据与状态修改同事务提交；重复输入返回已完成结果，相同幂等键而内容不同则报冲突。失败不得部分绑定事件，也不回滚 Git 已完成的提交。未实现的迁移版本、blob 缺失、基准对象缺失及游标冲突应有可区分错误。

## 已确认：工具调用内的提交无需独立切段机制

串行模式也存在嵌套边界：AI 的 Bash 调用可能先编辑再执行 git commit，post-commit 早于外层 PostToolUse。

提交 hook 读取当前工作区的调用状态，按两种情况处理：

```text
case 1：调用已结束
PreToolUse(S1) → AI 修改 → PostToolUse(S2) → 外部修改 → commit(R)
  S1→S2：已记录的 AI 事件
  S2→R ：提交边界补记的未知事件

case 2：调用尚在进行
PreToolUse(S1) → AI 修改 → commit(S2) → AI 修改 → PostToolUse(S3)
  S1→S2：提交边界记录的 AI 片段，归入本次提交
  S2→S3：调用结束记录的 AI 片段，留在新提交为 base 的后续段
```

两个相邻快照事件关联同一 ToolCall，沿用相同原因及来源元数据（原始原因缺失时仍为空）。提交时调用仍然进行，最新观测快照自然变成 S2；PostToolUse 只比较上一快照 S2 与新快照 S3。原始 pre_snapshot S1 不覆盖，也不另设 fragment_start_snapshot。一次调用多次提交时仍使用同一规则。

S2 指 post-commit 时实际工作区快照，不必等于新提交 tree。部分提交时，旧段仍在 AI 片段后追加 virtual_close，新段先记录 virtual_carry，再衔接 S2→S3。两个虚拟事件单独标记，不继承 AI 原因。若需要以新 base 表示 S2，可保存内容等价的新基准快照，而不修改旧快照。

一期串行假设下，工具期间的变化统一按工具事件归属，不额外推断其中由命令启动的格式化等子步骤。独立于工具调用发生的变化才补为未知来源。

缺少 PostToolUse 的失败/中断调用需要关闭或恢复调用状态，不能将永久遗留的 open 记录当作正在执行的证据；其具体恢复入口与判定规则仍待细化。

## 下一步逐项细化

1. 采集边界：仓库/worktree 身份、已跟踪和未跟踪文件、忽略规则、二进制、符号链接、子模块、外部路径。
2. 生命周期：配对、幂等、无变化调用、失败但部分修改、缺失后置事件、并发及恢复。
3. 快照：内容存储位置、内容寻址或 patch、清单、原子落盘、空间预算及回收。
4. 数据模型：仓库、会话、调用、观测、快照、文件变化、元数据来源、提交关联。
5. 存储接口：事务边界、迁移、SQLite 并发写入、错误语义、查询和内容对象一致性。
6. CLI：`motif hook` 的 stdin 协议、参数、输出、退出码；`motif init` 对 Agent hook 和 Git `post-commit` hook 的范围、检测、合并、重复执行和撤销。
7. 隐私：采集排除策略、敏感内容、原始 payload 是否保留、保留期限。
