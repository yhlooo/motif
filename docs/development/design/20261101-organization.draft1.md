# 提交关联与意图批次整理

状态：讨论草案，不作为实现依据。配套文档：[采集](20261101-capture.draft1.md)、[本地 Web](20261101-web.draft1.md)。

## 已确认的方向

- 消费统一的原始修改记录，与具体 Agent 的 Hook 协议解耦。
- 原始记录需要与 Git 提交建立关联，CR 涉及多个提交时能够汇集相关记录。
- 使用 Agent 将原始编辑过程整理为人类可阅读的意图批次。
- 保留原始记录供追溯，生成的解释不能改写原始事实。
- 延续总体设计：最终代码差异完整覆盖，不能把历史 patch 简单相加当作最终 diff。

## 已确认：同时保留 base commit 和最终 commit 关联

采集时未来提交尚不存在，因此先记录当时的 `base_commit`；创建提交后，通过 Git `post-commit` hook 补充实际提交关联。CR 查询需要使用最终提交归属。补充关联不会覆盖采集时的 `base_commit`。

部分提交采用下述成对虚拟事件方案，保持原始事件整体归组，无需将原始事件拆成分别归属多个提交的片段。

## 示例与待细化语义

例：HEAD 为 A，发生 E1、E2 后提交 B，再发生 E3 后提交 C。

简单场景：

- E1、E2 的采集基准是 A；E3 的采集基准是 B。
- E1、E2 若被完整提交到 B，可关联 B；E3 若被完整提交到 C，可关联 C。
- Review A→C 时汇集 B、C 关联的记录，并以 A 与 C 的真实差异为最终事实。
- 尚未提交的记录可以查看，不必等待产生提交才能保存。
- 原始事件保持不可变；提交关联单独保存，允许表达部分关联或未确定。

## 已确认：成对虚拟事件闭合提交

用户提出用一对互逆的虚拟修改事件闭合提交边界，避免拆分原始事件。以下给出状态化表达，并补充未知事件的计算顺序。

设 A 是本轮基准提交，W 是本轮原始事件按顺序应用后的状态，B 是实际新提交的 tree。原始事件必须能够从 A 完整重放到 W。

```text
A --原始事件序列--> W --patch1--> B --patch2--> W
patch1 = Diff(W, B)
patch2 = Diff(B, W) = Inverse(patch1)
```

- 将原始事件序列及 patch1 归入提交 B，其有序应用结果与 A→B 的提交差异一致。
- patch2 作为后续序列的起点，base_commit 为 B，保留未提交修改。
- patch1 与 patch2 记录为虚拟事件，并关联为同一对；不能伪装成 Agent 当时执行的操作或赋予虚构的修改原因。
- patch 的“求和”表示按顺序应用后比较结果，不是直接拼接 diff 文本；“负 patch”表示交换前后状态得到逆变换。

例：A 中值为 10，Agent 改为 30，但 B 只提交到 20。

```text
归入 B：原始事件 10→30，虚拟事件 patch1 30→20
留待后续：虚拟事件 patch2 20→30，base_commit=B
```

### 提交边界的计算顺序

设 S 是 base commit A 上最后一个已记录快照，C 是新提交 tree，R 是 post-commit 时实际工作区。锁定本轮待关联事件集合后：

1. 首先读取 C、R，确定剩余修改 `P = Diff(C, R)`（patch2），以及逆变换 `Q = Diff(R, C)`（patch1）。
2. 在上述剩余修改已明确的条件下，计算尚未采集的净变化 `U = Diff(S, R)`：调用已结束时记为未知事件；处于工具调用期间则记为当前调用的 AI 片段，原因与该调用一致。
3. 提交 C 的重放顺序为 `A --已有事件--> S --U--> R --Q--> C`，验证终态等于 C 后完成关联。R 成为最新观测快照；若调用未结束，保留其上下文，下一事件自然从 R 开始。
4. 新一轮以 C 为基准，以 P 作为 carry 事件，当前逻辑状态恢复为 R。

这一区分修正了前版“先生成未知事件再确定虚拟事件”的计算顺序。Q 的输入状态是 R，不能在 S≠R 时直接把 Q 应用到 S；事件按状态转换复合，不能按文本 diff 相减。工具调用之外的未采集格式化等变化归为未知；工具期间按该调用记录，不从逆向闭合事件推断操作者。调用跨提交仍复用相邻快照生成事件的统一规则，见采集文档。

首次采集从 A 补齐到首次前置快照；每次 AI 前置边界也补记未知事件。由此保持串行状态链。需继续定义数据库原子性、崩溃重试及重复 hook 幂等。

### Git 操作与历史同步

目标：通过 Git hook 同步或补充提交关联，使每个关联事件链的净结果等于对应提交 diff。证据及局限见 [研究](../research/20261101-codex-git-hooks.md)。

- amend/rebase：利用 post-rewrite 的 old/new 映射建立新提交投影；复用原始记录并补充未知/虚拟事件，保留旧提交历史，不能覆盖原始观测的 base commit。具体迁移规则待细化。
- reset：引用移动可由 reference-transaction 发现；不将 reset 自身伪装成新提交。soft/mixed/hard 的工作区效果应由快照确认。无通用 post-reset；路径级 reset/restore 的变化由下次观测补齐。
- 切换分支：已有提交绑定不冲突。通过 post-checkout 更新当前 worktree 的基准及快照游标，避免将 A→B 的切换直接计为开发编辑；携带的未提交修改按新基准保留。
- 新提交内容可从 Git tree 计算，但缺少 hook/快照时不能恢复已经被丢弃的未提交内容，也不能仅凭终态唯一推断原始事件在拆分/rebase 后的语义归属。
- merge 提交有多个父提交，必须选择事件投影的比较父节点；这属于尚待决定的语义，而非 tree 无法计算。

## 待讨论：按 Review 范围整理

以下为本轮提案，尚未确认为一期行为。旧总体设计建议任务结束自动整理；这里建议改为一期按需触发，是否取代旧建议需用户确认。

### 触发时机

用户在 motif web 中选择范围，点击“整理修改”后调用 Agent。工具 hook、提交 hook 只负责采集和提交关联，不调用整理模型。打开页面只加载已有结果，不隐式发起模型调用；用户可以主动重新整理。

原因：会话结束不一定意味着任务完成，提交也未必是 CR 的最终范围。按实际选择范围统一整理，能够跨提交归组，避免每次编辑或提交都消耗模型调用。

### 一次整理的输入

先固定仓库、基准和目标状态，再开始生成。提交引用解析为明确 OID；若目标包含未提交修改，先保存工作区快照。生成过程中继续编辑不会偷偷改变本次输入。

提供给 Agent：

1. 固定基准到目标的最终 diff，以及理解修改所需的代码上下文。
2. 范围中提交关联的原始事件，包含调用来源、模型、原始原因及未知来源标记。
3. 虚拟事件及其用途，明确其用于状态闭合而非新的开发意图。

范围外的事件若用于追溯 carry 来源，只作为补充来源引用，不把其全部修改纳入最终 diff。历史事件中的重复编辑、撤销修改可以帮助解释，但不能机械累加成批次 diff。

### 一次整理的结果

建议每批包含标题、说明、最终修改的归属引用、来源事件引用、意图来源类型及依赖。Agent 负责提出归组，Motif 校验结果：归属引用确实存在，最终修改无遗漏、无重复，不能由 Agent 任意生成新的代码或 patch 冒充已有差异。

最终修改的引用粒度（文件/hunk/更小编辑单元）尚待下一轮确认，本节不预设按文件分组。虚拟事件只参与状态和来源追溯，不单独生成“回退/恢复”的意图批次。

输入没有历史记录时，允许仅依据最终 diff 整理，说明标为事后推断，并提示原始采集缺失。没有最终变化时不调用 Agent。输出验证失败时保留最终 diff 和错误诊断，不发布看似完整的有效批次。

每次生成保存输入和结果版本。相同输入可复用已有结果；显式重新整理生成新版本，不覆盖原始记录。生成调用的具体执行方式、缓存判定和审阅状态迁移另行细化。

## 下一步逐项细化

1. 提交关联：以 Git `post-commit` 为补充关联入口；细化已提交 tree 的读取、匹配粒度及证据。明确 hook 缺失或失败的补偿、重复执行幂等，以及历史改写等其他操作的处理；不能假定一个入口覆盖所有操作。
2. 范围查询：起止提交、集合与拓扑、merge 策略、未提交工作区、记录缺失的可见性。
3. 批次模型：最终 diff 的分配单位、同一区域多次修改、抵消事件、来源追溯、依赖与覆盖验证。
4. 整理时机：手动、Review 时、会话结束；旧总体设计建议完成任务后自动整理，具体触发仍待讨论。
5. Agent 调用：运行方式、上下文、权限、结构化结果、超时、成本、失败重试和取消。
6. 结果持久化：输入版本、生成运行、批次、来源引用、人工调整、重新生成及审阅状态失效规则。
7. 验收：有历史但无最终变化、有最终变化但无历史、部分提交、重复整理及输出不完整。
