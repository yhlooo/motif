# 提交关联与意图批次整理

状态：讨论草案，不作为实现依据。配套文档：[采集](20261101-capture.draft1.md)、[本地 Web](20261101-web.draft1.md)。

## 已确认的方向

- 消费统一的原始修改记录，与具体 Agent 的 Hook 协议解耦。
- 原始记录需要与 Git 提交建立关联，CR 涉及多个提交时能够汇集相关记录。
- 使用 Agent 将原始编辑过程整理为人类可阅读的意图批次。
- 保留原始记录供追溯，生成的解释不能改写原始事实。
- 延续总体设计：最终代码差异完整覆盖，不能把历史 patch 简单相加当作最终 diff。

## 已确认：同时保留 base commit 和最终 commit 关联

采集时未来提交尚不存在，因此先记录当时的 `base_commit`；创建提交后，通过 Git `post-commit` hook 补充实际提交关联。CR 查询需要使用最终提交归属。补充关联不会覆盖采集时的 `base_commit`。

部分提交采用下述成对虚拟事件方案，保持原始事件整体归组，无需将原始事件拆成分别归属多个提交的片段。

## 示例与待细化语义

例：HEAD 为 A，发生 E1、E2 后提交 B，再发生 E3 后提交 C。

简单场景：

- E1、E2 的采集基准是 A；E3 的采集基准是 B。
- E1、E2 若被完整提交到 B，可关联 B；E3 若被完整提交到 C，可关联 C。
- Review A→C 时汇集 B、C 关联的记录，并以 A 与 C 的真实差异为最终事实。
- 尚未提交的记录可以查看，不必等待产生提交才能保存。
- 原始事件保持不可变；提交关联单独保存，允许表达部分关联或未确定。

## 已确认：成对虚拟事件闭合提交

用户提出用一对互逆的虚拟修改事件闭合提交边界，避免拆分原始事件。以下给出状态化表达，并补充未知事件的计算顺序。

设 A 是本轮基准提交，W 是本轮原始事件按顺序应用后的状态，B 是实际新提交的 tree。原始事件必须能够从 A 完整重放到 W。

```text
A --原始事件序列--> W --patch1--> B --patch2--> W
patch1 = Diff(W, B)
patch2 = Diff(B, W) = Inverse(patch1)
```

- 将原始事件序列及 patch1 归入提交 B，其有序应用结果与 A→B 的提交差异一致。
- patch2 作为后续序列的起点，base_commit 为 B，保留未提交修改。
- patch1 与 patch2 记录为虚拟事件，并关联为同一对；不能伪装成 Agent 当时执行的操作或赋予虚构的修改原因。
- patch 的“求和”表示按顺序应用后比较结果，不是直接拼接 diff 文本；“负 patch”表示交换前后状态得到逆变换。

例：A 中值为 10，Agent 改为 30，但 B 只提交到 20。

```text
归入 B：原始事件 10→30，虚拟事件 patch1 30→20
留待后续：虚拟事件 patch2 20→30，base_commit=B
```

### 提交边界的计算顺序

设 S 是 base commit A 上最后一个已记录快照，C 是新提交 tree，R 是 post-commit 时实际工作区。锁定本轮待关联事件集合后：

1. 首先读取 C、R，确定剩余修改 `P = Diff(C, R)`（patch2），以及逆变换 `Q = Diff(R, C)`（patch1）。
2. 在上述剩余修改已明确的条件下，计算尚未采集的净变化 `U = Diff(S, R)`：调用已结束时记为未知事件；处于工具调用期间则记为当前调用的 AI 片段，原因与该调用一致。
3. 提交 C 的重放顺序为 `A --已有事件--> S --U--> R --Q--> C`，验证终态等于 C 后完成关联。R 成为最新观测快照；若调用未结束，保留其上下文，下一事件自然从 R 开始。
4. 新一轮以 C 为基准，以 P 作为 carry 事件，当前逻辑状态恢复为 R。

这一区分修正了前版“先生成未知事件再确定虚拟事件”的计算顺序。Q 的输入状态是 R，不能在 S≠R 时直接把 Q 应用到 S；事件按状态转换复合，不能按文本 diff 相减。工具调用之外的未采集格式化等变化归为未知；工具期间按该调用记录，不从逆向闭合事件推断操作者。调用跨提交仍复用相邻快照生成事件的统一规则，见采集文档。

首次采集从 A 补齐到首次前置快照；每次 AI 前置边界也补记未知事件。由此保持串行状态链。需继续定义数据库原子性、崩溃重试及重复 hook 幂等。

### Git 操作与历史同步

目标：通过 Git hook 同步或补充提交关联，使每个关联事件链的净结果等于对应提交 diff。证据及局限见 [研究](../research/20261101-codex-git-hooks.md)。

- amend/rebase：利用 post-rewrite 的 old/new 映射建立新提交投影；复用原始记录并补充未知/虚拟事件，保留旧提交历史，不能覆盖原始观测的 base commit。具体迁移规则待细化。
- reset：引用移动可由 reference-transaction 发现；不将 reset 自身伪装成新提交。soft/mixed/hard 的工作区效果应由快照确认。无通用 post-reset；路径级 reset/restore 的变化由下次观测补齐。
- 切换分支：已有提交绑定不冲突。通过 post-checkout 更新当前 worktree 的基准及快照游标，避免将 A→B 的切换直接计为开发编辑；携带的未提交修改按新基准保留。
- 新提交内容可从 Git tree 计算，但缺少 hook/快照时不能恢复已经被丢弃的未提交内容，也不能仅凭终态唯一推断原始事件在拆分/rebase 后的语义归属。
- merge commit 不单独纳入 CR 审阅项；候选提交取源可达、目标不可达的非 merge 提交。最终 diff 使用 merge-base→source HEAD，合并独有的变化由最终未知补齐覆盖。

## 已确认：由 coding Agent 在轮次结束前整理

一期假设适合合并的 AI 修改都在同一对话轮次内：用户输入后，Agent 执行并回复构成一轮。分批由实际 coding Agent 完成，而非 Review 时另调模型事后解释。此前“按 Review 范围调用模型整理”的提案由本节取代，旧总体设计中相关触发和 Batch diff 定义后续需同步修订。

### Patch 与 Batch

- `patch` 是 edit_event 的命令行称呼，引用同一份变更事实，不再复制一套修改记录。
- Agent 创建的 batch 仅包含同一轮、同一工作区、同一提交边界内连续的 AI patch，不允许跨轮、跨 commit、不连续、混入未知变更或重复占用已分批 patch。即使修改原因相同也不能跨提交合并。
- 连续按真实修改事件的记录顺序判定，不能只过滤出 AI 行后称其为连续。无内容变化的工具调用不打断连续性。
- 所有连续未知变更自动合并为未知 batch，允许跨对话轮次，但必须在提交边界截断，不要求 Agent 编写原因；未知来源标记不能被 Agent 改成 AI。
- 技术性的 virtual_close/virtual_carry 不属于待 Agent 分批的 AI patch。提交本身已是 batch 边界，不能越过这对虚拟事件合并提交前后修改；未知 batch 不以轮次作为边界。
- batch 保存成员事件的顺序、标题与整理后的原因。它组织的是历史修改过程；不同 batch 可以先后修改同一行，不能要求历史 batch diff 在最终 diff 上互不重叠。

### 命令

```sh
motif patch ls --current-turn
motif patch get <uid>
motif patch-batch create --title="标题" --desc="整理后的修改原因" <uid1> <uid2> ...
motif patch-batch delete <batch-uid>
```

`ls` 以易读形式输出本轮事件及相关批次：patch 唯一 ID、原始原因、观测时间/区间、AI 或未知、已有 batch 归属，以及 batch UID、标题和整理后原因。不能只列未分批项，否则 Agent 缺少已完成部分的上下文。`get` 返回指定 patch 的实际 diff 与全部元信息。

`create` 由 Motif 检查成员合法性、同轮同工作区、同一提交边界、来源、连续性和已有归属，再原子创建 batch；校验失败不部分写入。原因缺失允许 Agent依据当前真实上下文补充，但整理说明与原始原因分开存储。传入顺序与真实顺序的校验、重复调用幂等方式后续细化。

`patch-batch delete <uid>` 删除分批关系，不删除原始 patch，也不回滚代码。成员恢复为未分批，之后可以 create 重建。若本轮 AI patch 因删除而未分批，下一次 Stop 仍要求完成。CR 刷新按 commit + batch/patch 身份匹配，仍存在的项保留决定和评论，源 batch 删除后新出现的未分批项或重建 batch 不继承旧批准；旧记录保留但退出当前展示，见 Web 文档。未知 batch 被删除后，后续自动归组可重建，具体触发在下一次快照/Stop 归组时。

提交前允许在当前未提交事件集合内创建 batch；提交后批次随其成员关联到该 commit。Stop 时本轮可能已有多个提交，需要分别分批，而不是只能整理当前 HEAD 之后的 patch。提交前后即使记录了同一 base_commit 的原始上下文，也应按实际提交边界区分，不能仅比较 base_commit 字段判定能否合并。

### Stop hook 门禁

安装同步 Stop hook，仍使用 `motif hook codex` 根据输入事件分派，不把业务逻辑留在 hook 脚本。

1. 确定 session + turn，并按统一快照规则记录当前状态，使新发现的变化进入事件序列；未知 patch 自动形成 batch。
2. 检查本轮是否仍有未分批的 AI patch。
3. 若有，输出结构化 block 和续做提示，提示中直接附当时 `motif patch ls --current-turn` 的结果，以及 get/create 的用法，要求 Agent 完成分批再结束。
4. Agent 继续在同一轮执行命令。再次触发 Stop 时重新检查，仍未完成则继续 block；全部完成或本轮无 AI 变化则放行。

只读取记录和创建 batch 的命令写入仓库外数据库，不应产生新的工作区编辑事件，避免整理本身不断制造待整理修改。若 Agent 在续做期间又修改代码，新增 AI patch 也须完成分批。

确认完成必须以数据库中实际归属为准，不能只相信 Agent 文本声称完成。`stop_hook_active` 不是跳过检查的条件。

采集或存储异常仍不阻断开发；“检查成功但有待整理 patch”的 block 是明确要求的正常控制行为，不是程序故障。hook 未运行、用户中断或进程被终止时允许留有未分批项，Web 按下述规则展示，不声称任何强制结束都能保证完整分批。

### 轮次标识与持久化

轮次以适配器、session_id、turn_id 及本机工作区上下文标识，不能以某次模型请求或某次 Stop 尝试作为一轮。Codex 已核实可在同一 turn 中多次 Stop block 后继续。

`--current-turn` 通过 shell 的调用身份与 PreToolUse 已写入的 turn 映射解析；不能假定 Git HEAD 能唯一标识轮次，也不能默认取数据库最后一轮。手动运行无法唯一确定本轮时应给出清晰错误，是否另加显式轮次参数待定。

建议数据库增加 `turns`、`patch_batches`、`patch_batch_members`：turn 保存身份及完成状态；batch 保存 AI/未知类型、标题、说明与所属范围；members 保存事件引用及顺序，约束单个原始 patch 不被重复分批。原始 edit_events 不被生成说明覆盖。具体 SQL 与未知 batch 增量维护待细化。

## 已确认：CR 读取批次与完整性补齐

`motif web` 创建及刷新 CR 时解析当前源/目标分支，直接读取对应 commit 的已有 batch，不重新调用 Agent 归组。仍在范围内且身份不变的项保留批准和评论；新项 pending；离开范围的项不展示。每次刷新发布一致的视图版本。

batch 不跨 commit，因此按完整提交选择 CR 时，相关 batch 可以整体纳入，不需要把一个原始 batch 裁成跨提交的部分。一期创建入口只选分支，不提供未提交工作区 CR；后续接口可扩展。历史改写后的批次关联规则仍需另行细化。

- 没有归入 batch 的 patch 单独展示，不丢弃或伪装成已整理内容。
- 按时间顺序组合相关 batch 与独立 patch，抵消、覆盖均按状态变化处理，不做 diff 文本相加。
- 将组合结果与 Git 最终 diff 校验，剩余差异统一放入最后一个虚拟未知 batch。该 batch 是 CR 的派生展示数据，不写入 `edit_events` 和 `patch_batches`；创建 CR 时的具体校验状态可保存在 CR 自身数据中。
- CR 的虚拟未知 batch 与提交闭合时入库的成对虚拟事件是两种机制，不能混用。
- 不完整历史或无法重放的 patch 应明确显示问题；必须先定义组合后的实际状态，才能用到目标状态的差异生成最后补齐。不能把“补齐”当作隐藏应用失败的理由。

最后虚拟 batch 应基于全部已展示修改（包括独立未分批 patch）计算，避免相同修改既独立展示又重复补入末尾。

## 已确认：提交闭合虚拟事件的 CR 展示

这对事件不需要 Agent 整理，按其关联提交是否在 CR 中处理：

| virtual_close 所在提交 | virtual_carry 所在后续提交 | 展示 |
|---|---|---|
| 在 | 在 | 互相抵消，不展示这对事件 |
| 不在 | 在 | 后半显示“之前暂存变更” |
| 在 | 不在 | 前半显示“revert 部分暂不提交内容” |
| 不在 | 不在 | 不属于本 CR，不展示 |

尚未归入后续提交的 carry 在一期分支 CR 中不纳入。名称“之前暂存变更”是展示标题，不声称内容在当时的 Git index 中。配对关系以存储的 pair ID 为依据，不能只按 patch 文本相似就消去。展示转换不删除原始事件。

## 已确认：历史改写准确迁移，无法推断则未知

保留旧提交上的原始事件和 batch。post-rewrite 仅新增旧→新映射以及新提交的记录，不原地改写历史。已有 CR 随分支范围刷新；新提交即使复用旧批次说明，也使用新的关联身份，不继承旧 commit 的批准。仍然处于当前范围的旧 commit 项则保留决定与评论。

- 仅改提交说明的 amend：tree 与比较基准未变时，复制事件/批次的提交投影，可复用相同内容，给新提交关联独立身份。
- 带代码变化的 amend：在旧提交已有序列后补充实际新增净变化；工具期间有证据则保留 AI 来源，否则未知。对新提交验证从其父 tree 到新 tree 的状态闭合，再建立新关联。
- 无冲突 rebase：按 old/new 映射重放旧事件于新父 tree，并重建前后快照；批次元数据通过来源映射继承，不能把旧基准快照直接当成新基准。新生成事件保存 origin_event_id、批次保存 origin_batch_id 等来源信息，原始观测不覆盖。
- squash/fixup：按旧提交顺序组合来源批次，可保留为多个 batch，无需跨轮重新合并；这些 batch 现在都归新提交。补齐实际新 tree 与组合结果的差异。
- 冲突解决、重新排序导致旧 patch 无法精确重放：只凭新旧末态不能唯一决定旧事件每一行的新归属。保留来源记录，受影响部分转为明确的未知补齐，不给无法验证的映射继承 AI 原因；只要求实际结果与新提交 diff 一致。
- 一个旧提交拆成多个新提交：按新提交逐个建立闭合记录，但旧 batch 不能直接复制到多个新提交并重复计算。能准确映射的部分迁移，其余按新提交的实际差异记为未知，避免重复计算，最后校验一致性。

该方案不宣称所有 rebase 已解决；post-commit 与 post-rewrite 的去重、处理时序及 drop 提交仍需细化。分支切换只调整观测基准，不移动既有批次；reset 后下一次快照补齐未知状态，遗留调用不能继续提供 AI 归属。

## 命令契约提案

- 所有 UID 为不透明稳定标识；命令接受完整 UID，不靠可变列表行号引用。默认文本输出，同时建议支持 `--format json`，便于脚本读取。
- `patch ls --current-turn` 按真实事件顺序，额外显示提交/未提交边界和 batch UID；来源缺失显示 unknown，不补造原因。虚拟事件独立标记且不算 Stop 待整理项。
- `patch get` 返回前后快照引用、base/final commit、来源调用与轮次、原始原因、时间、batch 归属、文本 diff 或二进制摘要。
- create 的 UID 可以内部排序为真实顺序；不连续、跨提交、跨轮、混入未知/虚拟项、部分已归组均失败且无写入。完全相同有序成员及相同标题说明的重试返回原 batch UID；同成员不同说明提示先 delete 重建。
- delete 不存在的 UID 返回“已不存在”，无副作用，便于重试；原始 patch 始终保留。命令成功返回 0，参数/校验错误返回 2，存储等执行失败返回 1；普通 CLI 与 hook 协议返回分开处理。
- `--current-turn` 先用 hook 已保存的当前调用身份定位；手动调用可增设 `--turn <uid>`，二者互斥，无法确定时不猜测。
