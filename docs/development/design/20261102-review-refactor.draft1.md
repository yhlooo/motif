# CR 范围、投影与存储职责重构

状态：用户已授权按本文实施重构。第 2 节为已确认范围模型，其余章节为本次实施方案；完成情况和验证另记于实现记录。

基线：`bebe21c`。问题依据见 [实现评审](../research/20261102-implementation-review.md)。相关现行设计：[Web](20261101-web.draft1.md)、[采集](20261101-capture.draft1.md)、[整理](20261101-organization.draft1.md)、[当前实现说明](20261101-mvp-implementation.md)。

## 1. 问题与目标

当前 CR 已保存 SourceOID、TargetOID、Base、Head，但服务每次读取仍先解析分支，导致这些已保存 commit 未能成为独立可读的范围依据。列表逐个刷新 CR，某个 CR 分支不存在即可令整个列表失败。

此外，详情、diff、评论和审批路径反复触发完整刷新。Git 树读取逐文件启动 cat-file，稀疏快照读写又反复解析基准树；部分 Git 操作通过 Store 回调发生在数据库事务内。问题相互放大：一次简单读取可能重建多个投影，并长时间持有数据库锁。

本次重构目标：

- CR 可仅凭明确 commit 范围读取、构建和审阅，分支更新失败不破坏已有结果。
- 投影生成与读取分离，相同输入复用已发布结果。
- Git 和大规模内容计算退出数据库事务，保留事务发布与版本校验。
- 拆清内容解析、领域规则、持久化职责，并保留现有采集和历史语义。

不扩展任意语义分组，不改变连续 batch 约束，不增加模型调用，不实现常规 GC 或 Git 私有保留引用；一期创建界面继续只接受分支。

## 2. 已确认：commit 决定范围，分支更新 commit

底层范围应支持任意明确 commit 段，不依赖分支存在。当前仅通过指定源/目标分支创建 CR，是入口限制。

每个 CR 同时保存：

| 数据 | 职责 |
|---|---|
| 源 commit、目标 commit | 决定当前 CR 范围的直接参数 |
| 源分支、目标分支 | 创建时解析 commit，后续用于更新 commit |
| merge-base、提交列表、投影结果 | 从明确 commit 参数计算的派生数据 |

分支删除最多导致更新 CR 失败，不能使 CR 数据异常，也不能使已保存范围失效。分支名不是读取已发布 CR 的必要条件。

现有 `source_oid`、`target_oid` 可承载上述 commit 参数，不重复增加另一组含义相同的字段。`base` 是比较用 merge-base，不能代替目标 commit；`head` 若保留，应始终等于当前投影的源 commit。

## 3. 范围与跟踪模型提案

领域模型拆为两个值对象：

```text
CommitRange { source_oid, target_oid, comparison_mode }
BranchTracking { source_branch?, target_branch? }
```

构建器只接收完整 commit OID。将 revision 表达式解析为 commit 是入口职责；解析完成后，不让 HEAD 或分支名等可变表达式进入构建器。未来直接指定 commit 创建时，可以不设置 BranchTracking。

本轮不改变比较算法：`comparison_mode=merge_base`，最终内容为 merge-base(target, source) → source，候选提交为 `target..source` 的逆向拓扑序非 merge 集合。在线性祖先范围中，这自然覆盖任意选定的提交区间；DAG 沿用已确认的可达集合和最终未知补齐语义。无共同祖先或多个最佳 merge-base 明确报错。本文不额外引入两点 diff 模式。

CR 保存的是**最后一次成功发布的范围与投影**。新分支 OID 先作为候选输入；只有构建及发布成功后才更新 CR 的 source_oid/target_oid。不会出现范围字段已经改变、审阅项仍属于旧范围的状态。

### 3.1 更新失败行为

| 场景 | 目标行为 |
|---|---|
| 两分支存在且 OID 未变 | 检查采集/分批版本，未变则复用投影 |
| 分支推进或非 fast-forward | 按候选 OID 构建并原子发布新版本 |
| 源或目标分支不存在 | 更新失败，保留完整的旧 commit 范围及投影 |
| 一端解析成功、一端失败 | 不进行单边范围更新 |
| 候选范围无法比较或构建失败 | 保留旧范围及投影，报告具体失败阶段 |
| 同名分支恢复 | 下次更新重新解析，按通常范围变化规则处理 |
| 已存 commit/tree/blob 实际缺失 | 明确报告对象缺失，不把分支缺失和对象缺失混为一谈 |

分支重新创建后的更新仍按现有分支跟踪语义执行，不猜测分支身份；新 commit 不因内容相似继承旧批准。删除分支也不自动改跟踪目标、关闭 CR 或清空批准。

一期继续假设 Git 对象存在，不承诺删除分支后经过 GC 仍永久可读。若实际对象缺失，CR 元数据、审批和评论仍保留，可依赖该对象的 diff 请求单独报错。

## 4. 投影发布与读取提案

### 4.1 职责分离

```text
分支输入 → TrackingResolver → 候选 CommitRange
                                     ↓
来源记录 → ProjectionBuilder → 待发布投影
                                     ↓
                            ReviewRepository.Publish
                                     ↓
                     指定版本的详情 / diff / 评论映射
```

`TrackingResolver` 负责解析分支，不读取或重写审阅状态。`ProjectionBuilder` 根据 commit 范围、事件和批次构建状态链，不访问可变分支。`Publish` 在短事务中检查版本并切换当前投影。

### 4.2 更新流程

1. 读取当前 CR、跟踪配置、投影版本及来源 revision。
2. 解析两端分支为候选完整 OID；任一失败则返回更新失败和当前可读版本。
3. 计算输入签名。若与已发布输入相同，跳过构建。
4. 在事务外加载不可变 Git 数据、解析快照、重放事件，构建审阅项、诊断与最终状态校验结果。
5. 发布前再次检查分支 OID；变化则有限重试。Git 引用与数据库不能组成跨系统事务，本次发布代表明确捕获的 OID 对；发布之后的引用变化由下一次更新处理。
6. 短事务校验原投影版本、跟踪配置版本、来源 revision；任一变化则放弃候选并重试。通过后将范围、提交集合、投影项及摘要原子发布。

输入签名至少包括 source_oid、target_oid、比较模式、来源 revision 和投影算法版本。不能只比较两个 OID：相同 commit 上分批关系删除、重建也必须刷新。第一步可沿用现有全局 Generation，之后再按仓库细化，避免先引入复杂失效机制。

内容寻址对象可以在事务外准备，失败发布不让它们成为可见记录。暂不增加 GC；不以常规清理为这次重构的前置条件。

### 4.3 读取与交互

- 列表只读已发布摘要，不为所有 CR 重建投影。每项显示当前范围、审阅状态和最近更新结果，单项失败不影响其他项。
- 打开详情时由前端先发起一次显式更新，满足现有“打开时更新”的交互；随后读取返回版本。更新失败则展示旧范围及提示，仍可阅读旧 diff 和评论。
- diff、评论映射等端点读取指定投影版本，不隐式更新分支。并行请求不会各自触发构建。
- 未提供必需版本的写请求拒绝；携带过期版本的写请求返回 409。版本切换后前端重新加载项目选择。
- 分支缺失不会阻止对当前已发布版本的审批、评论和回复。界面明确显示这些操作针对所示 commit 范围，不代表已跟上分支最新状态。

同一次读取先固定投影版本，并始终使用该版本的状态和项集合。第一阶段仅服务当前版本，旧版本请求返回 409，无需立即提供任意历史投影查询。请求已取得的不可变投影在该请求内不会因并行发布被替换。

### 4.4 版本、稳定身份和决定

投影描述范围、项顺序、状态及诊断；审批和评论是关联稳定项的可变审阅数据，审批本身不导致重新构建代码投影。数据库存储可先复用现有表，不要求立刻复制全部历史投影。

保留现有 commit + batch/patch 身份规则。范围变化时，同身份项保留本 CR 的决定，新身份 pending，退出范围的项隐藏并保留历史。派生未知项继续带内容摘要；原始评论位置不修改，按指定投影映射。批准多个项若提供批量操作，应同事务校验版本并提交，避免逐项成功一半。

## 5. 状态和诊断提案

分开表达三个问题：

| 维度 | 示例 | 作用 |
|---|---|---|
| 更新结果 | ok、source_branch_missing、target_branch_missing、range_unresolvable、build_failed | 能否获得候选范围并成功发布 |
| 最终状态闭合 | verified、failed | 投影组合是否还原该范围的最终内容 |
| 历史归属 | complete、partial、unavailable | 已观测记录能解释多少修改 |

“complete”仅表示已纳入记录均可投影且无未知补齐，不据此承诺实际开发过程没有漏采。必要时使用更明确的展示文案。

诊断使用结构化记录：code、stage、event_id/路径等关联信息、可读 message。投影失败路径和未知补齐分别保留，不能因为最终字节一致而删除历史问题。更新失败不改变旧投影的闭合状态，也不改变 CR 的 approved/in_review/changes_requested。

最近一次更新结果作为独立元数据记录，可包含 attempted_at、last_success_at 和失败信息，不因仅更新提示就递增内容投影版本。并发更新使用独立 attempt 序号避免旧失败覆盖较新的成功。实际存储错误不能被伪装为分支更新失败或正常空列表。

## 6. 模块边界与事务提案

不先进行全仓包重命名；先通过少量接口拆清职责，再按实际依赖决定是否提取新包。

| 职责 | 接口方向与边界 |
|---|---|
| Git 数据读取 | ResolveBranch、ReadTree、ReadBlobs；只读用户仓库，不依赖数据库事务 |
| 快照与内容解析 | 基准树 + 稀疏覆盖 → State；区分 Git OID 和 Motif 内容 hash，提供明确的内容读取接口 |
| 领域转换 | 采集事件转换、批次约束、投影组合；输入显式，返回待持久化结果，不启动外部进程 |
| 持久化 | 读取记录、校验 cursor/revision、原子写入；继续用 GORM 和现有 SQLite 驱动 |
| 应用服务 | 编排读取、计算、发布及重试；capture/review 各负责自己的用例 |
| Web | 请求校验、错误映射、版本传递和交互，不承担分支刷新算法 |

领域值类型逐步从 Store 实现中分离，避免出现 Git 读取依赖 Store、Store 又回调 Git 的运行时环。无需为每张表创建仓储接口；接口围绕快照准备、采集发布、审阅发布这些用例定义。

所有 `git` 子进程、文件内容读取、哈希和大规模投影在数据库事务外完成。事务内仍需执行依赖当前记录的批次合法性校验、幂等回执检查、外键/唯一约束检查和版本比较。不能为了缩短事务而放弃跨行规则原子性。

采集采用“读取 cursor → 准备状态和基准 → 计算转换 → 事务校验 cursor 并发布”。若竞争导致 cursor 变化，重新准备观察，不把旧观察强行挂到新链上；hook 的故障放行行为保持不变。串行采集前提仍然有效。

## 7. Git 与快照读取优化提案

- 按 repository/object format/OID 缓存不可变树、blob 身份和必要内容；缓存有容量限制，可丢弃，不承担历史存储职责。
- Git blob 使用批量 cat-file 读取，避免每文件创建进程；保留原始路径字节、mode、gitlink 和二进制语义。
- 同一基准树只解析一次，快照表示尽量保留稀疏覆盖；投影状态可共享不可变基准，避免每项反复复制和解析全仓状态。
- 精确 diff 和行映射按状态/内容身份缓存，审阅决定变化不使内容缓存失效。
- 输入未变时更新操作不重放事件。列表摘要查询不恢复所有 before/after 快照。

Git 引用不进入长期内容缓存。缺失对象和临时读取失败不长期缓存成“对象不存在”。多仓库共享 blob 的解析必须保留可用来源选择，缓存命中不混淆仓库身份。

先衡量 Git 子进程数量、读取字节数、树解析次数、投影次数、数据库事务持有时间及端到端延迟，再确定容量和进一步优化。不能把尚未测量的收益写成已验证结论。

## 8. 接口与数据迁移提案

应用层提供以下语义，名称可随编码规范调整：

```text
PreviewRange(commit_range)
CreateFromBranches(branches, expected_preview, title)
RefreshTrackedRange(review_id)
GetPublishedReview(review_id, expected_version?)
GetSelectionDiff(review_id, selection, view_version)
GetMappedThreads(review_id, selection, view_version)
SetDecision / AddThread / Reply (review_id, ..., view_version)
```

直接 commit 范围的构建和预览应能独立调用；一期 HTTP 创建入口仍只开放分支。无需为证明底层能力提前新增用户 CLI。

HTTP 列表与 GET 详情成为纯读取；显式更新沿用 POST refresh。更新失败响应同时区分失败信息和可继续读取的 published_version，前端再 GET 当前发布结果。存储/服务故障沿用错误状态，不兜底返回看似正常的空 CR。

迁移复用既有 source_oid/target_oid、分支字段、稳定项 ID 和评论锚点。增量添加比较模式、输入签名/构建版本、更新结果元数据，必要时增加跟踪配置版本。老数据的比较模式默认采用现有三点语义；分支已丢失时仍以保存的 OID 恢复，不要求重新解析分支才能迁移。不能从不存在的分支猜填缺失 commit。

不清库、不重编事件 ID，不修改原始事件和旧批次，不因架构重构重置审批。迁移后的首次构建沿用现有可证明身份匹配规则。

## 9. 实施顺序与验收

1. **范围解耦与故障隔离。** 提取 commit 范围构建入口；分支刷新失败保留旧范围。列表只读摘要，详情更新失败仍可打开。补源分支、目标分支分别删除的回归。
2. **投影读取与发布分离。** 统一输入签名和版本协议，diff/threads 不隐式刷新；前端打开时显式更新。保持审批、评论、历史身份语义。
3. **快照解析退出事务。** 先迁移 review 的读/发布路径，再迁移 capture/rewrite；保留游标冲突、来源 revision 和幂等检查，逐步移除 Store 的 Git 回调。
4. **批量读取与缓存。** 增加 OID 缓存和批量 cat-file，测量真实收益；最后依据实际耦合拆分领域类型和持久化实现。

验收至少覆盖：

- 不经分支，仅凭明确 commit 对可以构建同等范围；线性区间及 DAG 沿用现有比较结果。
- 创建 CR 后分别删除源/目标分支：列表、详情、diff、原审批和评论仍可读取；更新失败不改变 OID、项集合、版本和批准状态，其他 CR 正常。
- 一端推进另一端缺失时不单边发布；同名分支恢复、非 fast-forward 后按稳定身份规则更新。
- 分支解析成功但投影失败不覆盖旧结果；对象真实缺失单独诊断。
- 相同 OID 上 batch 删除/重建触发新投影；未变化输入不重放。并行 diff/threads 不各构建一次。
- 来源版本或 cursor 在构建期间变化时拒绝旧候选；过期写入返回 409。刷新失败时对当前发布版本的写入仍正常，之后的新投影按身份继承。
- 评论跨选择映射、删除位置隐藏、close/carry、amend/rebase/squash/split、旧库迁移和项目隔离继续通过现有回归。
- 通过测试注入检查外部 Git 读取不发生在 DB 事务内；性能记录同时提供冷缓存、热缓存和不同文件/批次数量结果，不用墙钟阈值替代正确性验证。

完成每一步后再扩大重构范围，避免同时改动所有模块而难以判断语义回归来源。
