# 本地 Web 审查工作流

状态：讨论草案，不作为实现依据。配套文档：[采集](20261101-capture.draft1.md)、[整理](20261101-organization.draft1.md)。标为“已确认”的是用户决定，其余为本轮实现提案。

## 已确认：一期工作流

`motif web` 提供本地 CR 列表、创建 CR、查看单个 CR。AI 分批已在 coding Agent 的 Stop hook 中完成，Web 不另调模型整理。

底层范围支持任意连续提交；一期交互仅选择源分支与目标分支，审阅源分支上新增的提交。其他创建方式后续扩展。数据库使用 `code_reviews` 保存创建过的 CR，以及批次批准状态、评论等关联数据。

用户查看没有采集记录的范围时提示“未采集到数据，可能未安装 hook 或 hook 运行失败”；不根据无记录断言具体原因，也不声称已有部分记录代表完整采集。

## 已确认：CR 页面

左侧按顺序列出 batch 和未归纳修改，右侧显示 diff。支持选择单项或连续多项，右侧同步显示所选项有序合并后的净 diff；不是简单拼接 patch 文本。未知 batch、未分批 patch、保留的提交虚拟事件和最后完整性补齐项均需有清晰名称。

可以在任意 diff 的单行或行范围评论，并回复评论。每个 batch 和未归纳修改均可批准或拒绝；所有审阅项批准后 CR 转为批准。Web 先实现简单 MVP，后续丰富交互。

## 已确认：CR 随源和目标分支刷新

假设 Git commit 一直存在，忽略 GC；与 commit 关联的 patch/batch 使用稳定身份。CR 保存源和目标分支，重新解析当前提交范围，而不是冻结为永不更新的提交列表。

- 新增 commit：仍在范围内的 batch/patch 保留本 CR 中已有批准、拒绝及评论；新增项初始 pending，CR 根据当前项重新汇总状态。
- 非 fast-forward 更新：不再属于当前范围的提交及其审阅项不展示；新提交的项按新身份展示，不因 diff 相似就继承旧批准。从界面看，被替换部分的批准被清空；仍在范围内且身份不变的项保留状态。
- 旧评论和决定可留在数据库，不将其绑定到新提交。将来同一身份再次出现时可以取回其记录；是否给历史记录单独页面不作为一期必需。
- 审阅状态是当前 CR 内的状态，不自动跨不同 CR 继承。源 batch 被删除重建时，新 UID 不继承旧 UID 的批准。

每次刷新仍解析明确 OID 并生成一个一致的视图版本；同一次列表/diff/评论/批准请求必须针对同一版本，不能在一次请求内部混用刷新前后的分支状态。版本只是读写一致性标记，不阻止 CR 随分支刷新。

## 已确认：采用 GitHub PR 的范围语义

底层支持提交范围，一期 UI 选择源分支、目标分支。采用 GitHub PR 的三点比较：最终 diff 为 `git diff target...source`，即 merge-base→source HEAD。提交列表取源可达、目标不可达的提交，按拓扑顺序从旧到新展示；不取任意单一最短路径，也不只取 first-parent。

MVP 忽略 merge commit 的独立审阅项：候选命令为 `git rev-list --reverse --topo-order --no-merges target..source`。这是 Git 可达集合枚举，与 `git diff` 的三点比较分别承担提交选择和最终内容校验。GitHub 文档的直接依据及实现推导见[研究](../research/20261101-github-review-range.md)。

merge tree 中有而非 merge 批次未覆盖的变化，继续由最终完整性校验补入 CR 虚拟未知项。范围变化时重新计算该派生项，不继承内容已经变化的虚拟项批准。

目标/源无共同祖先或有多个最佳 merge-base 等罕见情况，MVP 明确显示范围无法解析，不随机选基准。这是实现默认值，不阻塞常规分支。

## 提案：列表与状态

CR 列表默认显示进行中的 CR，提供全部/已批准过滤；每行显示标题、源/目标分支、创建时间、批准进度及拒绝标记。点击进入详情。

审阅项 `decision = pending | approved | rejected`，初始 pending；批准/拒绝允许改判。为覆盖用户所说的“所有批次批准”，所有可见且需要审阅的项目（含未归纳修改和非空虚拟补齐项）都参与汇总：

- 任意项 rejected：CR 为 changes_requested。
- 非空项集合全部 approved：CR 为 approved。
- 否则：CR 为 in_review。

批准是本地审阅状态，不执行 git merge，不删除代码；拒绝也不自动让 coding Agent 修改代码。无需自动触发模型。

## 已确认：diff 评论按 batch 和代码位置映射

评论保存创建时的 batch（未归纳 patch 则保存对应审阅项）、文件、old/new 侧及单行/行范围；保存原始位置，不在每次展示时改写原始行号。叠加选择不同 batch 后，按有序 diff 中的插入、删除及路径变化计算该位置在当前展示状态中的对应位置。映射后该行已不存在则不展示该评论；评论和回复仍保留。

连续选择 `[item_i,...,item_j]` 显示有序合并后的净 diff。在线性且验证连续的状态链中，可以比较第一项之前与最后一项之后的状态；非线性提交必须先构建一致的展示序列，不能直接取不连续快照端点。

实现提案：锚点额外记录创建时两端状态/hash，使用 diff 产生的行号映射，而非只加一个全文件行号偏移。被删除行不强行贴到最近的相似行。行范围可以保留可映射的子范围，无剩余可映射行时不显示。文件改名仅在有可靠路径映射时跟随，否则不猜测。old/new 两侧分别映射。

选择多个批次后发起评论，需要确定锚点对应的稳定 batch/item；可根据该行在所选序列中的来源映射记录。上下文行或最终虚拟项没有唯一原始 batch 时，记录对应视图项及状态锚点，不虚构事件来源。该项属于实现细节，MVP 按直觉选择可解释的归属。

评论线程保存作者展示名、正文、时间，回复通过 thread ID 关联。一期本地单用户，不要求账号系统。源提交离开当前 CR 时隐藏其评论，不迁移到新 commit；同一 batch 在不同合并视图中按上述映射显示。

## 提案：数据表

UID 为不透明 TEXT；时间为 UTC 微秒 INTEGER；行号为从 1 开始的 INTEGER。路径与内容身份沿用采集模块。核心表字段如下，外键默认限制误删；项目全量卸载显式按关联删除。

| 表 | 字段与约束 |
|---|---|
| code_reviews | id PK, repository_id FK, title, source_branch, target_branch, source_oid, target_oid, base_oid, head_oid, status, integrity_status, created_at, updated_at, view_version；source/target/base/head oid 保存最近一次已发布视图的解析结果 |
| code_review_commits | review_id FK, position, commit_oid, comparison_parent_oid；PK(review_id,commit_oid)，当前列表顺序为 position |
| code_review_items | id PK, review_id FK, position, kind, source_batch_uid NULL, source_event_uid NULL, title, description, before_snapshot_id FK, after_snapshot_id FK, decision, commit_oid, stable_key, active, content_digest；UNIQUE(review_id,stable_key)，position 在 active 项中唯一 |
| code_review_item_events | item_id FK, position, event_id FK；PK(item_id,position)，稳定成员及顺序 |
| code_review_comment_threads | id PK, review_id FK, anchor_item_id FK, anchor_batch_uid NULL, before_snapshot_id FK, after_snapshot_id FK, path, side, start_line, end_line, blob_sha256；CHECK(end_line>=start_line>=1) |
| code_review_comments | id PK, thread_id FK, author_name, author_email NULL, body, created_at；第一条为评论，之后为回复 |

item kind 为 batch、unbatched_patch、commit_virtual、integrity_unknown。末尾 integrity_unknown 仅写 CR 项，不写 edit_events/patch_batches。source_batch_uid 作为来源标识保存，不设删除级联，以便源 batch 删除后 CR 内容仍保留；原始事件仍存在，成员引用保持有效。标题说明可以缓存；刷新以源稳定身份匹配。旧项不在当前范围时设 active=false，保留决定及评论；新身份新增 pending 项。stable_key 包括 commit OID、项类型和 batch/patch UID；派生未知项还包含内容摘要，内容变化即视为新项。

常用索引：code_reviews(repository_id,status,created_at)、code_review_items(review_id,position)、comments(thread_id,created_at)。CR status 可缓存，但 SetDecision 必须在同一事务更新条目和当前 active 项汇总状态，读取时可重新计算验证。

## 提案：服务与 HTTP 接口

前端通过同一 Go 服务访问数据库，不能直接拼 SQL。

```text
ListReviews(repository, status, cursor)
PreviewReview(source_branch, target_branch)
CreateReview(preview_token, title)
RefreshReview(review_id)
GetReview(review_id)
GetSelectionDiff(review_id, first_item_id, last_item_id)
SetDecision(review_id, item_id, decision, view_version)
CreateCommentThread(review_id, selection, anchor, body, view_version)
ReplyToThread(thread_id, body)
```

Preview 固定分支 OID/输入摘要；Create 时若输入已变化则要求重新预览，不静默切换内容。创建或刷新 CR 的行、当前提交列表、审阅项 active 集合及汇总状态同事务发布；大 diff 计算在事务前完成。相同 Create 请求可带幂等键，避免双击创建重复 CR。

详情打开/主动刷新时重新解析分支，MVP 无需常驻监听；写请求校验 view_version，过期则要求重新加载，不向错误内容写入批准或评论。

HTTP 对应 `/api/code-reviews` 列表/创建、`/api/code-reviews/preview`、`/api/code-reviews/{id}`、`/{id}/diff?first=...&last=...`、`/{id}/items/{item}/decision`、`/{id}/threads` 和 `/api/comment-threads/{id}/replies`。状态变更使用 POST/PATCH，不用 GET。

## 提案：MVP 实现默认值

Go HTTP 服务 + 简单前端静态资源，构建后嵌入单一 motif 二进制。`motif web` 前台运行，默认绑定 127.0.0.1:端口，端口及自动打开浏览器的选项再定。数据仍在本机全局数据库中按仓库隔离。

前端先实现 CR 列表、分支选择表单、左右分栏、连续选择、diff、评论回复及批准拒绝。评论正文按文本渲染，代码按文本转义；本地写请求校验来源。没有跨用户协作、复杂筛选、自动修复或实时模型任务面板。
