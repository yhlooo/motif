# 本地 Web 审查工作流

状态：讨论草案，不作为实现依据。配套文档：[采集](20261101-capture.draft1.md)、[整理](20261101-organization.draft1.md)。标为“已确认”的是用户决定，其余为本轮实现提案。

## 已确认：一期工作流

`motif web` 提供本地 CR 列表、创建 CR、查看单个 CR。AI 分批已在 coding Agent 的 Stop hook 中完成，Web 不另调模型整理。

底层范围支持任意连续提交；一期交互仅选择源分支与目标分支，审阅源分支上新增的提交。其他创建方式后续扩展。数据库使用 `code_reviews` 保存创建过的 CR，以及批次批准状态、评论等关联数据。

用户查看没有采集记录的范围时提示“未采集到数据，可能未安装 hook 或 hook 运行失败”；不根据无记录断言具体原因，也不声称已有部分记录代表完整采集。

## 已确认：CR 页面

左侧按顺序列出 batch 和未归纳修改，右侧显示 diff。支持选择单项或连续多项，右侧同步显示所选项有序合并后的净 diff；不是简单拼接 patch 文本。未知 batch、未分批 patch、保留的提交虚拟事件和最后完整性补齐项均需有清晰名称。

可以在任意 diff 的单行或行范围评论，并回复评论。每个 batch 和未归纳修改均可批准或拒绝；所有审阅项批准后 CR 转为批准。Web 先实现简单 MVP，后续丰富交互。

## 提案：范围解析与固定输入

创建时保存源/目标分支名及当时 OID。通常分叉场景以 merge-base 为基准、源分支 HEAD 为目标，提交候选为源可达而目标不可达的提交；接口返回实际基准、提交列表和最终 diff 概览供确认。不能直接使用 target HEAD→source HEAD，把仅存在于目标分支的变化误算为本次开发修改。

底层以显式 base/head OID 及有序提交列表保存范围，不与分支名称绑定。含 merge 的提交序列与比较父节点仍需和历史同步规则一起验证；不能用不明确的时间排序处理 DAG。

创建 CR 时冻结该范围的批次标题、说明、成员及来源事件引用、每项的前后状态、最终 diff 和完整性校验结果。之后 branch 移动、patch-batch delete 或重新分批都不隐式改动已创建 CR。无新增提交时提示无可审阅内容；不自动创建空的已批准 CR。

一期暂不提供 CR 自动刷新及评论迁移。检测到分支新增/改写时显示输入已变化，可创建新 CR；旧 CR 继续可读。这是简化建议，尚待确认。

## 提案：列表与状态

CR 列表默认显示进行中的 CR，提供全部/已批准过滤；每行显示标题、源/目标分支、创建时间、批准进度及拒绝标记。点击进入详情。

审阅项 `decision = pending | approved | rejected`，初始 pending；批准/拒绝允许改判。为覆盖用户所说的“所有批次批准”，所有可见且需要审阅的项目（含未归纳修改和非空虚拟补齐项）都参与汇总：

- 任意项 rejected：CR 为 changes_requested。
- 非空项集合全部 approved：CR 为 approved。
- 否则：CR 为 in_review。

批准是本地审阅状态，不执行 git merge，不删除代码；拒绝也不自动让 coding Agent 修改代码。无需自动触发模型。

## 提案：diff 与评论锚点

连续选择 `[item_i, ..., item_j]` 时，计算第一项起始状态与最后一项结束状态的净差异；构建 CR 时应先验证展示项之间的状态连续。提交虚拟事件的消除/保留规则按整理文档执行，再建立展示状态链。无法重放的片段需要显式诊断，不能悄悄忽略。

评论定位不能只保存“文件第 42 行”，建议保存：CR ID、选择的起止 item ID、diff 两端快照引用、路径、old/new 侧、起止行号、对应侧 blob hash。这样同一路径在不同批次或合并选择视图中仍能区分。行范围一期限定同一文件同一侧，跨文件选择创建多条评论。diff 中上下文行也允许评论；二进制只有摘要，没有可定位的文本行。

评论线程保存作者展示名、正文、时间；回复通过 thread ID 关联。一期本地单用户，不要求账号系统；作者可从 Git user 配置取展示值，缺失则为本地用户。切换所选项后，仅在对应冻结视图中显示该视图评论，不猜测跨视图行号迁移；详情可汇总所有评论。

## 提案：数据表

UID 为不透明 TEXT；时间为 UTC 微秒 INTEGER；行号为从 1 开始的 INTEGER。路径与内容身份沿用采集模块。核心表字段如下，外键默认限制误删；项目全量卸载显式按关联删除。

| 表 | 字段与约束 |
|---|---|
| code_reviews | id PK, repository_id FK, title, source_branch, target_branch, source_oid, target_oid, base_oid, head_oid, status, integrity_status, created_at；source/target oid 是创建时解析结果 |
| code_review_commits | review_id FK, position, commit_oid, comparison_parent_oid；PK(review_id,position)，同 CR 提交不重复 |
| code_review_items | id PK, review_id FK, position, kind, source_batch_uid NULL, source_event_uid NULL, title, description, before_snapshot_id FK, after_snapshot_id FK, decision；UNIQUE(review_id,position) |
| code_review_item_events | item_id FK, position, event_id FK；PK(item_id,position)，冻结成员及顺序 |
| code_review_comment_threads | id PK, review_id FK, first_item_id FK, last_item_id FK, before_snapshot_id FK, after_snapshot_id FK, path, side, start_line, end_line, blob_sha256；CHECK(end_line>=start_line>=1) |
| code_review_comments | id PK, thread_id FK, author_name, author_email NULL, body, created_at；第一条为评论，之后为回复 |

item kind 为 batch、unbatched_patch、commit_virtual、integrity_unknown。末尾 integrity_unknown 仅写 CR 项，不写 edit_events/patch_batches。source_batch_uid 作为来源标识保存，不设删除级联，以便源 batch 删除后 CR 内容仍保留；原始事件仍存在，成员引用保持有效。源标题和说明在 CR item 中复制，不运行时反查以免变化。

常用索引：code_reviews(repository_id,status,created_at)、code_review_items(review_id,position)、comments(thread_id,created_at)。CR status 可缓存，但 SetDecision 必须在同一事务更新条目和汇总状态，读取时可重新计算验证。

## 提案：服务与 HTTP 接口

前端通过同一 Go 服务访问数据库，不能直接拼 SQL。

```text
ListReviews(repository, status, cursor)
PreviewReview(source_branch, target_branch)
CreateReview(preview_token, title)
GetReview(review_id)
GetSelectionDiff(review_id, first_item_id, last_item_id)
SetDecision(review_id, item_id, decision)
CreateCommentThread(review_id, selection, anchor, body)
ReplyToThread(thread_id, body)
```

Preview 固定分支 OID/输入摘要；Create 时若输入已变化则要求重新预览，不静默切换内容。创建 CR 的行、提交列表、冻结项及初始状态同事务发布；大 diff 计算在事务前完成。相同 Create 请求可带幂等键，避免双击创建重复 CR。

HTTP 对应 `/api/code-reviews` 列表/创建、`/api/code-reviews/preview`、`/api/code-reviews/{id}`、`/{id}/diff?first=...&last=...`、`/{id}/items/{item}/decision`、`/{id}/threads` 和 `/api/comment-threads/{id}/replies`。状态变更使用 POST/PATCH，不用 GET。

## 提案：MVP 实现默认值

Go HTTP 服务 + 简单前端静态资源，构建后嵌入单一 motif 二进制。`motif web` 前台运行，默认绑定 127.0.0.1:端口，端口及自动打开浏览器的选项再定。数据仍在本机全局数据库中按仓库隔离。

前端先实现 CR 列表、分支选择表单、左右分栏、连续选择、diff、评论回复及批准拒绝。评论正文按文本渲染，代码按文本转义；本地写请求校验来源。没有跨用户协作、复杂筛选、自动修复或实时模型任务面板。
